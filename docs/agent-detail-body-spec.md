## 1. 무엇을 왜 바꾸나

- '내 기준으로 자세히 보기'(상세 분석)가 모델에 공고 본문을 주지 않아, 무료 화면에 있는 내용만 되풀이하고 본문에 있는 내용을 "공고에 없다"고 틀리게 말한다.
- 바꾸는 것 두 가지
  1. 모델 입력에 공고 본문을 넣는다.
  2. 리포트 줄 수 상한을 올린다('나와 맞는 점' 최대 2줄 → 4줄, '지원 전에 할 일' 1~2줄 → 1~4줄).
- 측정 결과 (고치며 볼 30건 × 프로필 3종, 사람 정답 131개 기준, opencode 경로)

  | | 지금 방식 | D3 | 본문을 일반 AI에 그대로 |
  |---|---|---|---|
  | 정답 재현 | 14.8% | 47.3% | 62.8% |
  | 새 사실(정답에 새 사실 2개 이상인 공고, 리포트당) | 0.12 | 1.91 | 2.44 |
  | "공고에 없다" 오판 | 30줄 | 1줄 | 3줄 |
  | 근거율 | 82.8% | 95.0% | 83.1% |
  | 어긋남 줄 비율 | 9.9% | 1.5% | 2.3% |

- **D3은 평가 명세 §16.2의 합격선을 넘지 못했다**(정답 재현 70%, 새 사실 2개, 어긋남 1% 미달). 그래도 반영하는 이유: 지금 방식보다 모든 지표가 낫고, 지금 방식은 크레딧을 받고 틀린 안내를 한다. 평가 명세 §9의 "합격선을 못 넘기면 PR로 올리지 않는다"는 2026-11-24 팀장 결정으로 이 변경에 한해 푼다. 기록에는 '합격선 미달, 지금 방식 대비 개선으로 반영'이라고 적는다.
- 하지 않는 것: 리포트 칸 추가, 화면 구성 변경, 모델 교체, 외부 공고 찾기 변경, 역량 칸 지침 변경(D4, 효과 없음), 인용 대조(D2, 효과 없음).

## 4. 설계

### 4.1 본문 저장 (서버 전용)

- 모음: `notice_bodies`, 문서 id = `notice_id`
- 칸: `notice_id`, `body_text`, `notice_version`(쓴 시점의 게시본 버전), `updated_at`
- 쓰는 쪽: 배치가 공고를 게시(`publish`)할 때 같은 공고의 본문을 같이 쓴다. 게시하지 않는 공고(검토 대기, 미게시)는 쓰지 않는다. 게시본을 지울 때 본문도 지운다.
- 쓰기 횟수를 아낀다: 본문이 이미 같은 내용으로 올라가 있으면 다시 쓰지 않는다(게시본의 '같으면 건너뜀'과 같은 방식). 배치를 돌릴 때마다 전체를 다시 쓰지 않는다.
- 읽는 쪽: 상세 분석 요청 때만 1건 읽는다. 추천 목록·공고 상세·검색 응답에는 싣지 않는다.
- 앱에서 읽을 수 없어야 한다. `firestore.rules`가 이 모음의 앱 접근을 막는지 확인하고, 막지 않으면 막는 규칙을 더한다(규칙 배포는 팀장 지시 뒤).
- 본문에 든 내용: 수집한 공지 원문 그대로다. 학생 개인정보가 줄지어 나오는 명단형 공지는 지금 자료에 제목 기준 0건이다. 제목이 명단형(합격자·선발 결과·수상자·명단 발표)인 공고는 본문을 올리지 않는다(평가 도구 `ROSTER` 규칙과 같은 낱말).
- 이미지·첨부만 있는 공고(본문 20자 미만, 22건)는 올리지 않는다.

### 4.2 입력

- `build_messages`가 본문을 받아 user JSON의 `공고` 아래 `본문` 칸으로 넣는다. 다른 칸(제목, 분류, 요약, 마감, 지원 자격 판정, 활동 기간)은 그대로다.
- 본문은 4,000자까지 넣는다. 넘으면 앞 4,000자만 넣고 끝에 잘렸다는 표시를 붙인다. 4,000자는 평가에서 확인한 최대 길이(3,073자)보다 조금 큰 값으로 잡았고, 넘는 공고는 617건 중 5건이다.
- 본문이 없으면(저장 전 공고, 명단형, 본문 없는 공고) `본문` 칸을 빼고 지금처럼 동작한다. 요청을 실패시키지 않는다.
- 학생 쪽 입력(허용 목록, `build_payload`)은 바꾸지 않는다.

### 4.3 지침

- `backend/agent/harness/detail_analysis.md`에 평가에서 쓴 D3 사본(`tools/agent_eval_variants/detail_d3.md`, 평가 worktree)과 **같은 다섯 군데만** 고친다.
  1. "쓸 내용이 없으면 줄을 줄입니다." 한 줄 추가
  2. "fit" 최대 2줄 → 최대 4줄, "최대 2개만 씁니다. 3줄 이상 쓰지 않습니다" → "최대 4개만 씁니다. 5줄 이상 쓰지 않습니다"
  3. "todo" 1~2줄 → 1~4줄
  4. "입력의 '본문'은 공고 원문 전체입니다. 요약·마감·조건에 없는 일정, 장소, 진행 방식, 제출물, 혜택은 본문에서 찾습니다." 추가
  5. "본문에 있는 내용을 공고에 없다고 말하지 않습니다. '확인 필요'는 본문에도 없는 내용에만 씁니다." 추가
- 더할 문장 하나(평가에 없던 것): 본문 칸이 없을 때를 위해 "입력에 '본문'이 없으면 요약과 조건만으로 씁니다." 이 문장을 넣은 지침으로 §6.2 확인을 다시 한다.
- `VERSION`을 올린다(예: `detail-2026-11-24.1`). 지침 버전이 저장 키에 들어 있어 예전 리포트는 다시 만들어진다. 다시 만들 때 크레딧이 어떻게 되는지 `service.py`에서 확인해 보고에 적는다(바꾸지는 않는다).

### 4.4 후처리

- `scrub_codes`, `split_long_lines`는 그대로.
- `ground_report`의 역량 줄 대조는 평가에서 쓴 방식으로 맞춘다: 근거 후보를 '원문에서 확인할 조건' 뒤에 본문 줄을 덧붙인 것으로 본다. '(우대)' 표시는 원래 조건에서만 붙인다. 본문이 없으면 지금과 같다.
- 판정은 지금처럼 코드(`evaluate`)가 한다. 모델이 본문을 읽고 판정을 바꾸지 않는다(D-039).

### 4.5 앱

- 계약·화면 구성은 바꾸지 않는다.
- 리포트가 길어진다(중앙값 약 1.35배, 최대 848자). 리포트 화면이 긴 리포트에서 깨지지 않는지만 확인한다(§6.4). 고칠 곳이 나오면 고치지 말고 화면 사진과 함께 보고한다.
- §3의 2번 문구는 지금 안내 문구가 있는 화면·문서에 더한다(`apps/mobile/lib/ui/legal.dart`, `agent_flow.dart`의 요청 전 안내, `docs/agent-privacy-spec.md` §2). 앱 문구는 해요체를 쓰지 않는다(D-020).

### 4.6 로그·개인정보

- 본문, 프롬프트, 응답 원문은 지금처럼 로그에 남기지 않는다. 남기는 것은 공고 id, 지침 버전, 토큰 수, 비용, 본문 사용 여부(있음·없음·잘림)까지다.
- 모델에 가는 학생 정보는 지금과 같다.

## 6. 검증

### 6.1 시험

- `uv run pytest -q` 전체 통과. 새 시험이 다뤄야 할 것
  - 본문이 있을 때 user JSON에 `본문` 칸이 들어가고, 없을 때는 빠진다
  - 4,000자 초과 본문이 잘리고 표시가 붙는다
  - 명단형 제목, 본문 20자 미만 공고는 본문을 쓰지 않는다
  - 게시하지 않는 공고는 본문을 쓰지 않고, 게시본 삭제 때 본문도 지워진다
  - 추천 목록·공고 상세 응답에 본문이 실리지 않는다
  - 역량 줄이 본문에 근거가 있으면 남고 없으면 빠진다. 본문이 없으면 지금과 같은 결과
  - 지침 파일이 §4.3의 여섯 군데(다섯 + 한 문장) 말고는 바뀌지 않았다
- 이 PC의 `.venv` 파이썬은 임시 폴더를 못 잡아 일부 시험이 환경 때문에 실패할 수 있다. 평가 때처럼 `--basetemp`를 scratchpad로 주거나, 실패한 시험 이름을 그대로 적는다.

### 6.2 평가와 같은 결과인지 (opencode, 0원)

- 평가 도구로 고치며 볼 30건 × 프로필 3종을 **운영 코드 경로**(`build_messages` + 새 지침 + 후처리)로 다시 돌린다. 본문은 평가 고정본(`data/local/agent_eval/sample/records.json`)에서 준다.
- 평가 D3 실행과 같은 입력에서 user JSON이 같은지(본문 칸 포함) 기계로 대조한다. 지침은 한 문장이 달라 system은 다르다.
- 채점은 평가와 같은 방식(방식 이름 가림, 사람 정답 기준). 평가 D3 수치(정답 재현 47.3%, 근거율 95.0%, 어긋남 1.5%, "공고에 없다" 1줄)와 나란히 적는다. 채점 흔들림(같은 리포트 재채점 일치율 약 91~95%) 안이면 같다고 본다.
- 본문 없는 경로: 30건 중 10건을 본문 없이 돌려 지금 방식과 형식·규칙 위반 수(`harness_check.check`)가 같은지 본다.
- 보지 않는 10건은 쓰지 않는다.

### 6.3 운영 경로 (DeepSeek API, 팀장 승인 뒤)

- `tools/harness_check.py`의 기본 3건을 본문을 넣어 돌린다. 형식 오류 0, 규칙 위반 수, 입력·출력 토큰, 건당 비용, 응답 시간을 지금 값과 나란히 적는다.
- 할증 시간대(평일 한국 시간 10~13시, 15~19시)에는 돌리지 않는다. 3건을 넘기지 않는다. 키는 `harness_check.api_key()`로 읽고 출력·저장하지 않는다.
- 건당 원가가 지금의 2배를 넘으면 멈추고 보고한다.

### 6.4 화면

- 에뮬레이터에서 실제 공고로 리포트 화면을 본다(메모 `reference-real-data-emulator-check` 방식 또는 프로젝트의 시험 화면). 평가에서 가장 긴 D3 리포트(848자)와 중앙값 근처 리포트 하나씩을 넣어 화면 사진을 남긴다.
- 볼 것: 잘림·넘침 없음, 칸마다 4줄일 때 스크롤로 다 읽힘.

## 8. 실행 규칙 (받는 에이전트용)

### 8.1 작업 위치

- `main`에서 새 worktree와 브랜치를 만든다(예: `.claude/worktrees/detail-body`, `feat/detail-body-input`). 메인 폴더에는 팀장의 미커밋 문서(`docs/final-prep-todo.md`, `docs/stage2-results.md`)가 있으니 건드리지 않는다.
- 평가 worktree(`57499b6156ed-4`)는 읽기만 한다. 그 브랜치의 시작 커밋에는 팀장의 미커밋 문서가 들어 있으므로 그 브랜치를 병합하거나 그 위에서 작업하지 않는다.
- 평가 도구와 결과 문서(`tools/agent_eval_*.py`, `tools/agent_eval_variants/`, `backend/agent/tests/test_agent_eval.py`, `docs/agent-quality-eval.md`, `docs/agent-quality-eval-spec.md`)는 새 브랜치로 파일만 옮겨 온다. 이 명세도 같이 넣는다. §6.2에 평가 도구가 필요하다.
- `data/`는 git 제외다. 메인 폴더의 `data/local`을 절대 경로로 읽는다. 기존 worktree는 지우지 않는다.

### 8.2 건드리지 않을 것

- `backend/recommendation`(불러 쓰기만), `contracts/`의 앱 계약, 외부 공고 찾기(`backend/agent/external.py`, `external_*.md`), 크레딧 규칙, 앱 화면 구성.
- 새 라이브러리·유료 서비스 추가 금지.
- **하지 않는다**: 배포, Firestore에 실제로 쓰기(본문 올리기 실행 포함), 보안 규칙 배포, APK 빌드. 전부 팀장이 따로 지시한다.
- 실호출: opencode는 자유, DeepSeek API는 §6.3의 3건만, 팀장 승인 뒤.

### 8.3 보고

- AGENTS.md §5 형식: 바꾼 파일, 실행한 검증(명령과 실제 결과), 남은 문제, 다음 작업.
- 더해서: §6.2의 나란히 표, opencode 호출 수, API 호출 수와 금액, 화면 사진 경로, 본문 올리기 건조 실행 결과(올릴 건수·빠지는 건수와 사유), 예전 리포트 재생성 때 크레딧 동작.
- 커밋·PR은 팀장이 말할 때만 한다. 커밋 문구는 짧게 쓰고 AI 꼬리말을 붙이지 않는다.

## 9. 한계

- D3은 평가 합격선 미달이다. 본문을 일반 AI에 그대로 준 것보다 정답 재현이 낮다(47% 대 63%). 대신 근거율과 어긋남에서 낫다.
- 수치는 고치며 본 30건 기준이다. 보지 않는 10건 최종 측정은 사람 정답지가 들어온 뒤 따로 한다.
- 어긋남·근거율 채점은 Claude가 했고 사람 재검토 20%가 아직 없다.
- 평가는 opencode 경로였다. 운영 경로는 3건으로 형식만 확인한다.
- 줄 수를 늘리면서 근거 없는 줄이 10줄에서 26줄로, 억지 연결이 12줄에서 17줄로 늘었다(리포트 90개 기준).
- 4,000자 넘는 본문(5건)은 뒷부분을 읽지 못한다. 첨부·이미지 속 내용은 여전히 읽지 않는다.
- 평가 표본 30건 중 13건은 측정일에 앱에 보이지 않는 과거 공고였다(게시일 기준으로 평가).
