# 맞춤 에이전트 품질 평가 명세 (상세 분석·학교 밖 기회 찾기)

- 작성일: 2026-11-23
- 상태: **제안 (팀장 승인 전, 미실행)**
- 근거 문서: [decisions.md](decisions.md) D-039·D-044·D-047, [agent-privacy-spec.md](agent-privacy-spec.md) §2·§12.1, [harness/README.md](../backend/agent/harness/README.md), 2026-11-23 대화
- 이 문서는 측정 방법과 완료 기준만 정한다. 코드·지침·계약은 바뀌지 않았고, 실호출도 하지 않았다.
- 2026-11-24 고침: 1단계 결과 검토 뒤 평가 기준 날짜를 공고별 게시일로 바꿨다(§3, §5.1, §5.4). 이미 만든 1단계 결과물을 고치는 일은 §15에 있다.
- 2026-11-24 더함: 1차 결과를 보고 2차 실행 후보와 합격선을 정했다(§16). §9의 제안값은 §16.2로 바뀌었다.
- 2026-11-24 더함: 2차 결과(세 변경안 불합격)를 보고 상세 분석 변경안 D3·D4를 정했다(§17).
- 받는 에이전트는 §14(실행 규칙)를 먼저 읽고, 지금 할 일인 §17(3차 실행 지시)을 따른다. §15·§16은 끝난 일이다. 문서 안의 'Claude'는 이 명세를 실행하는 에이전트를 뜻한다.

## 1. 목표와 범위

- 목표: '내 기준으로 자세히 보기'(상세 분석)와 '학교 밖 기회 찾기'(외부 공고 찾기)가 크레딧을 받을 만한지 숫자로 판정한다. 못 미치면 기능마다 가장 큰 원인 하나만 고치고 같은 숫자로 다시 증명한다.
- 판단 기준: D-039 확장 기준 "일반 AI에 없는 자료를 쓰는 기능만". 공고 원문을 일반 AI에 붙여 넣은 결과보다 나아야 한다.
- 하지 않는 것: 칸·기능·화면 추가, 지침 문장부터 고치기, 모델 교체.

## 3. 결정 (2026-11-23 팀장)

- 실호출 경로
  - 상세 분석 측정은 전부 opencode 구독으로 한다(0원). `harness_check.py`의 `OpencodeProvider`와 같은 설정
  - DeepSeek API는 웹 검색이 필요한 외부 찾기에만 쓴다. 잔액이 2달러(약 2,800원)라 시연 몫을 남긴다. 상한은 §6.6
- 공고 본문: 평가용으로 본문을 그대로 보낸다. 공고의 문의 연락처는 가리지 않는다
  - 사람 이름이 줄지어 나오는 명단형 공지(합격자·선발 결과·수상자)는 표본에서 뺀다. 지금 자료에는 제목 기준 0건
- 0단계 사례: 표본으로 먼저 진행한다. 팀장이 "크레딧 값이 안 된다"고 느낀 실제 결과를 주면 실패 유형 분류에 덧붙인다
- 평가 기준 날짜 (2026-11-24 팀장): 게시일 기준 평가. 표본은 다시 뽑지 않고, 공고마다 '오늘'을 그 공고의 게시일로 준다
  - 이유: 고정된 표본 40건 중 18건(종료 10, 60일 넘은 마감 미상 8)이 측정일 기준 앱 추천 목록에 없다. 알림톡 14건은 전부 여기에 든다. 알림톡은 일반 AI에 없는 자료라 빼지 않는다
  - 리포트는 원래 공고가 살아 있을 때 만들어지므로 그 시점을 재현한다

## 5. 상세 분석 측정

### 5.1 표본

- 40건. 고치며 볼 30건과 끝까지 보지 않는 10건으로 나눠 고정한다(난수 씨앗 기록).
- 층: 출처 묶음 × 분류 × 본문 길이(3분위)

  | 출처 묶음 | 전체 | 측정일에 앱 추천에 보이는 것 | 표본 | 표본 중 보이는 것 |
  |---|---|---|---|---|
  | 명지 알림톡 | 302 | 12 | 14 | 0 |
  | 명지 홈페이지 게시판 | 201 | 98 | 12 | 8 |
  | 교외(위비티·콘테스트코리아) | 71 | 71 | 10 | 10 |
  | 숭의 | 36 | 29 | 4 | 4 |

  - '보이는 것'은 `lifecycle_status`가 closed·removed가 아니고 `ranking.is_stale`(마감 미상인 채 게시 후 60일 초과)도 아닌 공고다. 측정일은 2026-11-24.
- 안내형 분류(행정·학사·행사·기타)를 8건 넣는다. 더할 것이 없는 공고를 가려내는 기준(§8 D3)의 근거가 된다.
- 200자 미리보기 공고, 명단형 공지, 본문이 20자 미만인 공고(22건: 게시판 14, 숭의 8)는 뺀다.
- 표본은 2026-11-24에 고정한 40건(씨앗 20261124)을 그대로 쓴다. 다시 뽑지 않는다.
- 평가 기준 날짜: 공고마다 '오늘'을 게시일(`published.date`)로 준다. 게시일이 없는 교외 공고는 측정일(2026-11-24)로 준다.
  - 기준 날짜에 이미 신청 마감이 지난 공고가 있으면 건수와 공고 id를 결과 문서에 적는다(뽑을 때의 "마감 지난 공고 4건까지" 규칙은 이 확인으로 대신한다).
- 수치는 전체 40건과 '측정일에 보이는 22건'으로 나눠 적는다.

### 5.2 프로필

- 3종. 학교는 공고 출처 학교에 맞추고, 교외 공고는 명지로 둔다.

  | 이름 | 내용 | 보는 것 |
  |---|---|---|
  | P1 | 컴퓨터 계열 2학년 재학, 칩: 파이썬·팀 프로젝트 / 방학 / 서울 | 지금 시험 프로필과 같음 |
  | P2 | 비IT 계열 1학년 재학, 칩: 아직 없음 / 학기 중 / 경기·인천 | 경험 없는 저학년 |
  | P3 | 최종 학년 휴학, 칩 선택 안 함 | 미충족·확인 필요, 칩 없는 경로 |

### 5.3 정답지

- 단위: 원문 본문만 보고 "알면 지원 여부나 준비가 달라지는 사실"을 공고당 최대 5개. 0개도 답이다.
- 칸: 공고 id, 사실(한 문장), 원문 문장(그대로), 종류(자격 / 일정 / 장소·방식 / 과업·제출물 / 혜택 / 비용·조건 / 기타), 무료 화면에 있음(예 / 아니요)
  - '무료 화면'은 앱 공고 상세 화면이 크레딧 없이 보이는 칸이다. 칸 목록은 구현 때 화면 코드에서 확인해 양식 머리에 적는다.
- 작성
  - 고치며 볼 30건: Claude가 리포트를 보기 전에 초안을 쓰고 파일을 고정한다(해시 기록).
  - 그중 무작위 10건: 팀장과 팀원이 초안 없이 따로 쓴다.
  - 보지 않는 10건: 팀장과 팀원만 따로 쓴다. Claude는 최종 측정 전까지 이 10건의 본문과 정답을 보지 않는다.
- 일치도: 같은 원문 문장을 가리키면 같은 사실로 본다. 사실 단위 일치율(둘 다 적은 사실 ÷ 한쪽이라도 적은 사실)을 사람-사람, 사람-초안으로 낸다. [board_gold_agreement.py](../tools/board_gold_agreement.py) 방식.

### 5.4 비교 대상

| 이름 | 입력 | 지침·후처리 |
|---|---|---|
| A 지금 방식 | `build_messages` 그대로(요약·판정·조건) | `detail_analysis.md` + 운영 후처리 |
| G 일반 AI 기준선 | 프로필 + 제목 + 본문 전체 | 4칸 이름과 줄 수만 알려 줌. 귀띔 지침·서버 판정·후처리 없음 |

- A와 G 모두 '오늘'은 §5.1의 공고별 기준 날짜를 쓴다. A는 `build_messages(..., today=기준 날짜)`, G는 지시문에 같은 날짜를 적는다.
- G는 "원문을 일반 AI에 붙여 넣은 학생"의 결과다. 양식을 같게 두는 이유는 D-039 시험에서 형식 차이가 순위를 가른 적이 있어서다.

### 5.5 채점

| 지표 | 정의 | 방법 |
|---|---|---|
| M1 어긋남 | 원문이나 서버 판정과 어긋나는 주장 수 | 주장 단위 표시 |
| M2 근거율 | 원문에서 근거 문장을 찾을 수 있는 주장의 비율. 프로필 값을 그대로 옮긴 말은 주장에서 뺌 | 주장 단위 표시 |
| M3 정답 재현 | 리포트가 담은 정답 사실 ÷ 정답 사실 | 정답지 대조 |
| M4 새 사실 수 | 리포트가 담은 정답 사실 중 '무료 화면에 없음'인 것의 수(리포트당), 0개인 리포트 비율 | 정답지 대조 |
| M5 고정 문장 | `skills`·`todo`가 고정 문장으로 끝난 비율 | 기계 |
| M6 형식·규칙 위반 | 판정 불일치, 영어 코드, 문체, 줄 수 | `harness_check.check` 재사용 |

- 주장 단위 표시: Claude가 방식 이름을 가린 채 1차로 하고, 사람이 무작위 20%를 다시 채점해 일치율을 적는다. 근거 후보 문장은 두 글자 묶음 겹침(`prompt._grams`)으로 먼저 뽑아 준다.
- 비율에는 신뢰구간을 같이 적는다([evalstats.py](../tools/evalstats.py)).

### 5.6 호출 수 (opencode 구독, 0원)

- 기준선: A 120회 + G 120회. 변경안 비교: 후보당 90회, 최대 2개. 최종: 30회씩.
- 합계 약 450~500회. 입력이 같으면 다시 부르지 않게 저장하고, 끊겨도 이어서 돈다.

## 6. 외부 찾기 측정

### 6.1 질의

- 고치며 볼 12개: 공고 분류 4종 × 관심 분야 3종. 그중 4개에는 한 줄을 넣는다. 프로필은 P1에서 관심 분야만 바꾼다.
- 보지 않는 6개: 최종 측정 때만 쓴다.
- 목록은 첫 호출 전에 `queries.json`으로 고정한다.

### 6.2 실행

- 운영과 같은 흐름을 로컬에서 재현한다: `build_search_messages` → `web_search` → `ground_items` → `read_pages` → `judge_items`. 크레딧·저장소는 거치지 않는다.
- 기준선은 12개를 한 번씩, 그중 4개는 두 번 더 돌린다(같은 질의의 결과가 얼마나 바뀌는지). 합계 20회.
- 응답 원본, 단계별 집계, 미충족으로 빠진 결과까지 저장한다.

### 6.3 결과 페이지 직접 가져오기

- 응답 직후 결과 링크를 한 번씩 가져온다. 같은 사이트는 3초 간격, robots.txt가 막은 경로는 가져오지 않는다.
- 막힘·로그인·빈 본문은 '확인 못 함'으로 따로 센다. 본문은 `data/local`에만 두고 다시 싣지 않는다.

### 6.4 채점

| 지표 | 정의 |
|---|---|
| E1 링크 열림 | 열리고, 본문에 공고 이름의 핵심 낱말이 있음 |
| E2 마감 유효 | 가져온 본문의 접수 마감이 오늘 이후인 비율. 앱에 표시된 마감이 본문과 같은지 |
| E3 인용 일치 | 원문 읽기 단계가 낸 인용문이 가져온 본문에 문자열로 있는 비율(공백·기호 정리 후) |
| E4 자격 판정 | '충족'으로 나간 결과 중 본문과 맞는 비율. 미충족으로 빠진 것 중 실제로는 지원할 수 있던 것 |
| E5 쓸 수 있는 결과 수 | 요청 1번당 열림 + 마감 유효 + 지원 가능 + 학생이 직접 신청하는 공고 수. 과금됐는데 0개인 요청 비율 |
| E6 중복 | 앱에 이미 있는 공고와 같은 결과의 비율(D-048 묶기 규칙 재사용) |
| E7 안정성 | 같은 질의 3회의 결과 주소 겹침 |
| E8 재현율 | 정답 풀에서 찾은 비율(§6.5) |
| E9 비용·시간 | 요청당 원, 초 |

- 마감·자격 읽기는 Claude 1차, 사람이 무작위 20% 확인.

### 6.5 재현율 정답 풀

### 16.4 상세 분석: D1, D2

- 시험용 지침과 입력 조립은 `tools/` 아래에 따로 둔다(예: `tools/agent_eval_variants/`). `backend/agent/harness/*`와 `backend/agent/*.py`는 고치지 않는다. 합격선을 넘긴 뒤에만 운영 코드로 옮기고, 그때 따로 지시한다.
- D1
  - 지금 방식의 입력(`build_messages`)에 공고 본문 전체를 한 칸 더한다. 서버 판정, 후처리(`scrub_codes`, `split_long_lines`), 4칸 형식은 그대로 둔다.
  - 지침은 `detail_analysis.md` 사본에 본문 칸 설명과 "본문에 있는 내용을 없다고 말하지 않는다"만 더한다. 다른 문장은 고치지 않는다.
  - `ground_report`의 역량 고정 문장 규칙은 본문이 있을 때 본문 대조로 바꾼 것과 그대로 둔 것 중 하나만 고르고, 고른 쪽과 이유를 적는다.
- D2
  - D1에 더해, 공고에 관한 줄마다 본문에서 그대로 옮긴 인용을 받는다. 서버 판정이나 학생 정보만 말하는 줄은 근거 종류를 표시하게 한다.
  - 인용이 본문에 문자열로 없으면(`quote_in`) 그 줄을 뺀다. 인용은 검증에만 쓰고 리포트에는 넣지 않는다(계약 변경 없음).
  - 빠진 줄 수, 칸이 비게 된 리포트 수를 같이 적는다.
- 실행: 고치며 볼 30건 × 프로필 3종, 방식마다 90회(opencode). 같은 기준 날짜, 같은 정답 초안.
- 채점: 같은 지침(`grading/GRADING.md`), 방식 이름 가림. 채점자 흔들림을 보려고 1차의 A·G 리포트를 공고 10건만큼 섞어 다시 채점하고 1차 채점과의 일치율을 적는다.
- 같이 적을 것: 입력 토큰과 건당 원가 추정(운영 단가 기준, 지금의 2배를 넘으면 표시), 응답 시간, "공고에 없다" 줄 수.
- 보지 않는 10건은 이번에도 돌리지 않는다.

### 16.5 외부 찾기: X2, L

- 1차에 저장한 실행 12회(1회차)를 그대로 재료로 쓴다. 새 검색은 하지 않는다.
- L(안 열리는 링크 빼기): 가져오기 상태가 404, 접속·인증서 오류, 다른 경로로 넘어감인 결과를 목록에서 뺀다. 로그인·robots는 빼지 않는다.
- X2(교외 수집분 먼저): 측정일 고정본의 교외 수집분에서 살아 있고 마감이 남았고 분류가 질의와 같고 `evaluate` 판정이 미충족이 아닌 공고를 먼저 채운다. 관심 분야가 맞는 것을 앞에 두고, 부족분만 웹 결과로 채운다. 같은 공고는 D-048 규칙으로 묶는다.

### 17.1 근거

### 17.2 변경안

- 둘 다 D1(`tools/agent_eval_variants/detail_d1.md`와 그 입력·후처리)에서 시작한다. 운영 코드(`backend/agent/harness/*`, `backend/agent/*.py`)는 고치지 않는다.
- **D3 = D1 + 줄 수 상한**
  - 지침 사본에서 줄 수만 바꾼다: "fit" 최대 2줄 → 최대 4줄, "todo" 1~2줄 → 1~4줄. "eligibility"(1~3줄)와 "skills"(최대 4줄)는 그대로 둔다.
  - 줄 수와 맞물린 문장("최대 2개만 씁니다. 3줄 이상 쓰지 않습니다")만 숫자에 맞게 고친다. 다른 문장은 건드리지 않는다.
  - "한 줄에 한 가지 내용", 꼬리표('맞음:' 등), 문체 규칙은 그대로다. 줄을 채우려고 내용을 지어내지 않도록 "쓸 내용이 없으면 줄을 줄입니다"는 유지한다(지침에 이미 있으면 그대로, 없으면 한 문장 더한다).
