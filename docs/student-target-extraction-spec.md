## 1. 문제

**2026-11-26 운영 데이터 확인**

- 프로필: 명지전문대·경영학과·2학년·재학
- 게시 중인 공고(행정 공지 제외) 297건 중 '확인 필요'가 279건(94%)이다.
- 그중 필수 조건을 하나도 찾지 못한 공고는 218건이다.
- 218건 가운데 83건(교외 57, 명지 26)은 본문에 '대학생', '재학 중', '휴학생' 같은 대상 낱말이 있는데도 조건이 없다.
  - 교외 사이트의 대상 칸 줄('응모대상: 일반인, 대학생', '참가대상: 누구나, …, 대학생, 대학원생, 일반인')을 조건으로 읽지 않는다.
  - 규칙 추출기는 학적 낱말로 '재학생·휴학생·졸업생·졸업자'만 본다. '대학생', '대학(원)생', '재학 중인 …', '재학 또는 휴학 중인 …'은 읽지 않는다.
  - 외부 공고 찾기(`backend/agent/external.py`)에는 '대학생 → 재학·휴학' 규칙이 따로 있다. 같은 낱말을 두 기준으로 판정한다.

**같은 낱말이 신청 대상이 아닌 경우**

- '강화군 대학생 등록금 지원 사업', '대학생 진로준비도검사', '대학생 교육 프로그램입니다' 같은 사업·프로그램 이름

**'누구나'의 수식 범위를 따지지 않음**

- '18세 이상 대한민국 국민 누구나'를 지금 규칙은 명시적 제한 없음으로 읽는다(2026-11-26 공소청 국민기자단 공고 확인, LLM 보강이 나중에 내림).

**지금 계약으로는 '재학은 맞음, 휴학은 모름'을 표현할 수 없다**

- 조건은 맞음/틀림만 담는다.
- 그래서 '대학생'만 적힌 공고는 휴학생을 근거 없이 충족이나 미충족 중 하나로 정해야 한다.

## 2. 대상 문맥 판별

아래 문맥에 있는 대상 낱말만 조건 후보로 본다. 그 밖의 '대학생'은 무시한다(지금과 같음).

**대상 문맥인 것**

- 대상 항목 이름이 붙은 줄. 교외 사이트의 대상 칸 줄을 포함한다.
  - 예: '응모대상:', '참가대상:', '모집 대상:', '지원 대상:', '신청 대상:', '참여 대상:', '대상:', '지원 자격:', '신청 자격:', '응모 자격:', '참가 자격:'
- 필수 독립 제목('■ 지원 자격', '모집 대상' 등)이 연 구역 안의 줄(D-056 §3.1)
- 대상 표지가 붙은 구절
  - 예: '대학생 대상', '대학생이면 누구나', '…인 대학생'(문장의 주어·보어), '대학생으로 …인 자'

**대상 문맥이 아닌 것**

- 제목
- 사업·프로그램 이름 안의 낱말
- 안내 문장
- 제출 서류 이름('재학증명서')
- D-056 §3.7의 안내 줄

우대 구절 안의 대상 낱말은 조건이 아니라 우대다(D-056 그대로).

## 3. 대상 낱말과 학적의 대응 (원문이 뒷받침하는 범위까지만)

### 3.1 판정 방식

한 대상 문구에 나열된 낱말은 "이 중 하나에 해당하면 대상"으로 본다. 학생 프로필의 학적(재학·휴학·졸업) 하나하나를 세 가지 중 하나로 정한다.

- **확인됨**: 나열된 대상 중 하나에 해당한다고 원문이 뒷받침한다. → 조건 `value`
- **미확인**: 해당하는지 원문으로 알 수 없다. → 조건 `unconfirmed_values`(§4)
- **해당 없음**: 나열된 어떤 대상에도 해당하지 않는다고 원문이 뒷받침한다. → 어디에도 넣지 않음, 즉 미충족

### 3.2 낱말별 대응

| 원문 낱말 | 확인됨 | 미확인 | 비고 |
|---|---|---|---|
| 재학생, 재학 중(인 학생·대학생) | 재학 | - | 지금 '재학생'만 읽음 → '재학 중'을 더함 |
| 휴학생, 휴학 중 | 휴학 | - | 지금과 같음 |
| 재학 또는 휴학 중, 재·휴학생 | 재학, 휴학 | - | |
| 졸업생, 졸업자, 기졸업자 | 졸업 | - | 지금과 같음 |
| 대학생, 대학(원)생, 대학교 학생, 전문대학생 | 재학 | 휴학 | 졸업생은 대학생이 아니다 |
| 일반인 | - | 나머지 전부 | '일반인' 한 낱말로 어떤 학적도 확인되지 않고, 제한 없음도 만들지 않는다. 다만 학생이 아닌 사람도 대상이라는 뜻이라 다른 낱말로 확인되지 않은 학적은 미충족이 아니라 미확인으로 둔다 |
| 성인, 청년, 만 N세 이상, N세 이상 | - | '성인'·'청년'이 대상 하나로 나열되면 나머지 전부 | 나이 조건이다. 학적으로 판정하지 않고 직접 확인(미해석)으로 남긴다. '대학생, 성인'처럼 대상 하나로 나열되면 학생이 아닌 사람도 대상이라 '일반인'처럼 다룬다(구현 검토 2026-11-26). '재학생(만 20~69세)'처럼 숫자 나이가 대상을 꾸미면 학적 값을 바꾸지 않는다 |
| 대학원생 | - | - | 프로필에 대학원생이 없다. 학적 값을 더하지 않는다. 대학원생만 대상이면 직접 확인 |
| 졸업예정자 | - | - | D-046. 같은 문구에 재학을 덮는 낱말(재학생·대학생)이 있으면 값을 더하지 않는다. 없으면 지금처럼 직접 확인 |
| 청소년, 중·고등학생, 초등학생, 유치원 | - | - | 대학생 프로필과 관계없다 |
| 외국인, 직장인, 지역주민, 시민, 기타 | - | 나머지 전부 | 학적을 확인하지 않는다. 학생이 아닌 대상도 있다는 뜻이라 '일반인'과 같이 다룬다 |

**사이트 대상 칸과 본문이 모두 있을 때 (구현 검토 2026-11-26)**

- 교외 사이트가 붙인 대상 칸('응모대상:', '참가대상:')은 본문보다 거칠다. 본문에 대상 문구가 있으면 본문을 따르고, 대상 칸은 본문에 없을 때만 쓴다(원문 우선).

**나열 뒤에 범위를 넓히는 말**

- '등', '외', '및 그 밖에 관심 있는 누구나'가 붙으면, 확인되지 않은 학적은 미충족이 아니라 미확인으로 둔다.

### 3.3 휴학생 포함·제외가 명시된 경우: 원문 우선 (팀장 결정)

- '대학생(휴학생 포함)', '재학생 및 휴학생', '대학생(휴학 중 포함)' → 휴학 확인됨
- '대학생(휴학생 제외)', '대학생. 단, 휴학생은 신청 불가' → 휴학 해당 없음(미충족)
  - 대상 문구 바로 뒤나 괄호 안에서 그 대상의 학적을 좁히는 경우다.
  - 이때는 D-023(누구를 빼는 줄은 직접 확인)의 예외로 둔다. 확인됨 값에서 휴학을 뺀 조건을 만든다.
- 대상 문구와 떨어진 별도 줄의 제외 문구('휴학생 및 재등록생은 추천 불가'처럼 다른 맥락이 섞인 줄)는 지금처럼 직접 확인(D-023)이다.
- 졸업생 포함·제외도 같은 규칙이다(예: '대학생(졸업생 포함)').

### 3.4 '누구나'의 수식 범위 (팀장 결정)

'누구나'는 신청 대상 전체를 수식할 때만 명시적 제한 없음의 근거가 된다(D-056 §3.4 보완).

**전체를 수식함 → 명시적 제한 없음**

- '누구나 지원 가능', '참가 자격: 누구나'
- 사이트 대상 칸에서 '누구나'가 독립 항목인 경우: '참가대상: 누구나, 유치원, …'
  - 다른 항목은 누구나에 포함되는 예시다.

**한정어가 붙음 → 명시적 제한 없음 아님**

- 예: '대학생이면 누구나', '본교 재학생 누구나', '18세 이상 대한민국 국민 누구나', '13세 이상 누구나'
- 한정어를 §3.2로 판정한다. 대학생 → 학적 조건, 나이·국적 → 직접 확인.

### 3.5 조건 만들기

- 나열 전체에서 확인됨·미확인 학적을 모아 `enrollment_status` 조건 하나를 만든다(`in`).
  - 확인됨이 하나도 없으면 학적 조건을 만들지 않는다. 미확인만으로는 조건을 만들지 않는다.
  - 이때 대상 문구('응모대상: 일반인')는 원문 근거를 단 직접 확인 항목(`note: null`)으로 남긴다. 대상 문구를 찾았으므로 '지원 조건을 찾지 못했습니다'나 3(b)의 '본문에서 지원 대상을 찾지 못했습니다'로 보이면 안 된다.
  - 근거는 대상 문구가 있는 줄이다.
- 예
  - '지원 대상: 대학생' → `value: [enrolled]`, `unconfirmed_values: [on_leave]`. 졸업은 해당 없음.
  - '응모대상: 일반인, 대학생' → `value: [enrolled]`, `unconfirmed_values: [on_leave, graduated]`
  - '응모대상: 일반인' → 학적 조건 없음(확인됨 없음), 대상 문구를 직접 확인 항목으로 남김
  - '재학 또는 휴학 중인 대학생' → `value: [enrolled, on_leave]`
- 학교 조건('본교', 출처 학교 이름)과 학과·학년 조건은 지금 규칙 그대로다.
- 다른 미해석 조건(평점·소득·거주·연령·국적 등)은 그대로 둔다. 학적 조건이 생긴다고 그것들이 사라지지 않는다.

## 4. 계약 변경 (팀장 결정 (가))

**`eligibility_condition`에 선택 필드 `unconfirmed_values`를 더한다**

- 배열이고 `value`와 같은 값 영역이다. `value`와 겹치지 않는다.
- `operator: in`에만 쓴다. 이번에는 `enrollment_status`에서만 만든다.
- 없으면 빈 배열로 본다. 지금 저장된 데이터는 그대로 유효하다.

**`condition_result.unknown_reason`에 값 `value_unconfirmed`를 더한다**

**판정기 (`backend/recommendation/eligibility.py`)**

- 프로필 값이 `value`에 있으면 `met`
- `unconfirmed_values`에 있으면 `unknown`, 사유 `value_unconfirmed`
- 프로필 값이 없으면 지금처럼 `unknown`, 사유 `profile_missing`
- 그 밖이면 `not_met`
- 전체 판정 규칙은 그대로다. `unknown`이 있으면 확인 필요다.

**앱 (`report_screen.dart` 체크리스트)**

- `value_unconfirmed`인 학적 줄은 '직접 확인'으로 보인다.
- 안내 문구는 '{학적 이름} 포함 여부가 공고에 명시되지 않았습니다'이다.
  - 휴학 → '휴학생 포함 여부가 공고에 명시되지 않았습니다'(팀장 지정 문구)
  - 졸업 → '졸업생 포함 여부가 공고에 명시되지 않았습니다'
- 프로필을 다시 입력하라는 안내는 넣지 않는다.
- 결론 카드의 확인 개수에는 지금처럼 센다.

**SPEC·스키마·결정 기록**

- SPEC §5 EligibilityCondition·§6 지원 조건: 미확인 값의 뜻과 판정을 적는다.
- `common.schema.json`, `recommendation_item.schema.json`의 enum을 고친다.
- 결정 기록에 새 번호(D-057 이상, 파일 기준 다음 번호)를 쓴다. D-023·D-056 §3.4에서 바뀌는 점을 함께 적는다.
- `schema_version`은 유지한다. 선택 필드와 enum 값을 더할 뿐이고, 옛 데이터는 새 판정기에서 같은 결과를 낸다.

## 5. LLM 보강·외부 공고

- LLM 조건 경로도 같은 대응표를 따른다.
  - 대상 문맥(§2)이 아닌 근거로 만든 학적 조건은 버린다.
  - '대학생' 근거로 휴학을 확인됨에 넣은 응답은 `unconfirmed_values`로 옮긴다.
  - '일반인'만 근거로 학적을 확인한 응답은 버린다.
- 외부 공고 찾기(`external.py`)
  - '대학생 → 재학·휴학' 규칙을 이 대응표로 바꾼다.
  - 외부 공고 판정도 같은 판정기를 쓰므로 휴학생은 확인 필요가 된다.

## 6. 완료 기준

### 6.1 단위 사례

- 규칙만 쓴 경우와 LLM 응답을 고정한 경우를 모두 확인한다.
- 프로필은 명지전문대·경영학과·2학년이고, 학적만 바꿔 본다.
- 각 사례는 항목 목록 전체(조건 근거·`value`·`unconfirmed_values`, 미해석 항목)를 정확히 비교한다.
- 판정은 실제 판정기로 확인한다.

| 원문 | 조건 | 재학 | 휴학 | 졸업 |

### 6.2 실제 공고 비교 (두 숫자를 나눠 보고)

**대상**

- 로컬 660건 전체(이전 = 그때 main 규칙, 이후 = 이번 브랜치, 규칙만)
- 그중 게시 중 297건(`notices.json` 기준, 행정 공지 제외)

**보고 1: 대상 문구를 새로 찾은 건수**

- 학적 조건이 새로 생긴 공고 수(출처별)
- 새로 생긴 조건 전부의 근거 문구, `value`, `unconfirmed_values` 목록
- 원문과 대조해 대상이 아닌 곳에서 읽은 사례(프로그램 이름 등)를 따로 센다. 목표는 0건이다.
- 명시적 제한 없음이 새로 생기거나 사라진 공고('누구나' 수식 범위)를 따로 적는다.

**보고 2: 그 근거로 판정까지 달라진 건수**

- 프로필 세 가지(경영학과 2학년 재학 / 휴학 / 졸업)별 이전 → 이후 판정 변화표
- 판정이 바뀐 공고 목록
- 대상 문구를 찾았지만 판정이 그대로인 공고는 남은 사유별 건수로 나눈다.
  - 사유: 첨부·이미지, 다른 직접 확인 항목, 학과, 미확인 학적
- 미충족이 새로 생긴 공고는 전부 원문과 대조해 판정 근거를 적는다(특히 졸업 프로필).

### 6.3 실행과 반영 순서

**검증 명령**

- `uv run pytest -q -p no:cacheprovider`
- `uv run python tools/validate_contracts.py`
- `apps/mobile`에서 `flutter analyze --no-pub`, `flutter test --no-pub`

**분석 버전**

- 그때 main과 열린 PR이 쓰는 번호와 겹치지 않는 다음 번호로 올린다. #170이 `rule-0.13`을 쓰므로 `rule-0.14` 이상이다.

**운영 반영 순서 (팀장 지시 후)**

1. 서버를 먼저 배포한다. 옛 판정기는 `unconfirmed_values`를 모르고 휴학생을 미충족으로 본다.
2. 앱을 낸다. 옛 앱도 새 사유를 일반 '직접 확인'으로 보여 주므로 깨지지 않는다. 지정 문구는 새 앱부터 보인다.
3. 배치 폴더를 갱신하고 게시분을 다시 분석한다(정기 배치 + 범위 밖 일회성).
