## D-004. 개발환경·인증·서버 방식 (T3)

- 상태: **확정** (2026-10-18, 팀장 결정으로 확정)

- 참여자: 팀장 (팀원 확인 전)
- 근거: SPEC §4·§10·§12, docs/next-work-spec.md T3

### 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| Flutter / Dart | **3.47.7 / 3.13.5** (stable) | 2026-10-08 공개된 최신 stable. 두 사람이 같은 버전을 씀 |
| Flutter 의존성 고정 | `pubspec.lock` 커밋 | Flutter 기본 방식, 추가 도구 없음 |
| Python | **3.12** (마이너 고정) | LLM·수집 라이브러리와 서버 런타임 호환성이 가장 넓음 |
| Python 의존성 고정 | **uv + `uv.lock`** 커밋 | 무료·오픈소스. Python 버전과 하위 의존성까지 고정 |
| 로그인 수단 | Firebase Authentication **Google 로그인** 하나 | 앱에서 비밀번호를 다루지 않음. 사용자 식별은 인증 정보(uid)에서 얻음 |
| 서버 실행 환경 | **Cloud Run** | 같은 Python 컨테이너를 로컬과 서버에서 실행. 순수 추천 함수를 API로 감싸기 쉽고 Python 버전을 직접 고정 가능 |
| 수집·분석 배치 | **팀장 PC 로컬 실행** | 로컬 LLM 우선 평가(SPEC §4)와 맞고 GPU 서버 비용 없음. 배치가 멈춰도 게시된 공고 조회·추천은 Cloud Run·Firestore로 유지 |
| 로컬 LLM 실행 도구 | **Ollama**로 평가 | MIT 라이선스, 로컬 HTTP API로 분석 인터페이스 뒤에 두기 쉬움 |
| Android 검증 | 개발은 **에뮬레이터**, M1 통합·시연은 **실기기** | 시연 영상·실기기 검증 요건(SPEC §8·§11) |
| 개발·운영 분리 | Firebase 프로젝트 **dev / prod 2개** + 로컬 Firebase Emulator | 운영 데이터로 수동 실험 금지(SPEC §10) |

### 경계

- 요청 처리(인증된 API: 프로필·추천·저장)는 Cloud Run, 수집·정규화·LLM 분석·검증·게시는 로컬 배치가 맡습니다. 같은 기능의 백엔드를 두 군데 두지 않습니다(SPEC §4).
- Cloud Run API는 요청마다 Firebase ID 토큰을 검증하고 uid로 사용자를 식별합니다. 앱 입력의 사용자 ID를 믿지 않습니다.
- 로컬 배치의 Firestore 쓰기 권한(서비스 계정)은 Git에 저장하지 않습니다(SPEC §10, AGENTS.md §4).

### 영향

- Cloud Run과 Firebase(Firestore·Authentication 실사용)는 결제 계정이 연결된 Blaze 요금제가 필요합니다. 무료 한도 안에서도 비용 0원을 보장하지 않습니다(SPEC §4).
- 이 결정은 Firebase·GCP 프로젝트 생성·배포 승인이 아닙니다. 생성은 팀장의 별도 요청 후 진행합니다.
- uv, Ollama는 팀원도 설치해야 할 수 있습니다(Ollama는 배치를 맡는 팀장 PC만 필요). 웹 프레임워크(예: FastAPI)와 Flutter 패키지 추가는 각 작업에서 따로 승인을 받습니다.
- `.env.example`은 실제 변수가 생기는 작업에서 이름·설명만 추가합니다.

- **귀띔 브리핑:** 하루 첫 실행 때 전체 화면으로 보여 주고, 말풍선 섹션이 차례로 올라온다. "확인했어요"를 누르면 홈으로 간다. 그 뒤에는 홈의 "오늘의 귀띔" 카드에서 다시 연다. 하루 첫 실행 여부는 기기에만 저장하고 서버에 보내지 않는다. **전할 소식이 없는 날은 브리핑을 띄우지 않는다.**
- **홈** (기존 추천 탭): 오늘의 귀띔 → 다가오는 마감(2주) → 나에게 맞는 공고 → 저장한 공고 마감 변경. 하단 탭은 홈·저장·프로필.
- **공고 리포트** (기존 상세): 한 줄로 말하면 → 저장 후 마감 변경 → 지원 전 체크리스트(조건별 원문 근거) → 이래서 추천했어요 → 일정 → 하단 저장·학교 공지에서 보기.
- "AI 분석 리포트"라는 이름은 쓰지 않는다. 브리핑 문장은 템플릿이고 사용자별 LLM 생성이 아니다(LLM 실시간 브리핑은 P0 제외).

시각 스타일 (v2)

| 항목 | 값 |
|---|---|
| 바탕·카드 | 홈·브리핑 `#F3F4F8` 바탕에 흰 카드(모서리 20~26, 말풍선은 왼쪽 아래 6). 리포트는 흰 화면 |

| 상태색 | 급한 마감(7일 이내) `#D22030`/`#FFF0F0`. 확인 필요는 리포트 체크리스트에서만 주황(`#A34700`, 점선 상자), 목록 칩은 회색 |

- 토스 로고, 토스페이스 이모지, Toss Product Sans 글꼴 등 토스 자산은 쓰지 않는다.

데이터 표시 규칙 (SPEC §5·§6을 화면에 옮긴 것)

- score와 %는 보여 주지 않는다. 건수와 추천 이유(reason_codes 템플릿)만 보여 주고, 브리핑·리포트에 "합격 가능성을 뜻하지 않아요"를 적는다.
- **실제 자료에서는 "조건 확인 필요"가 대부분이다** (2026-10-20 실제 43건: 자동 비교 못 한 조건이 있는 공고 34건, 명시적 제한 없음 0건). 그래서 목록에서는 확인 필요를 경고색이 아닌 회색 칩으로 보이고, 리포트 체크리스트에서만 어떤 조건을 직접 확인해야 하는지 원문 근거와 함께 주황으로 보인다.
- "누구나 지원 가능"은 explicitly_unrestricted일 때만 쓴다. 조건을 찾지 못한 공고는 "공고에서 지원 조건을 찾지 못했어요"로 따로 보인다(빈 조건 ≠ 제한 없음).
- 확정 마감일이 없는 공고(선착순 등 deadline_note만 있는 공고)는 D-day를 달지 않고 "다가오는 마감"에서 뺀다. 뺀 건수를 알린다. 2주 안 마감이 없으면 그렇게 쓴다.
- 날짜만 확인된 마감은 시각을 보여 주지 않고 "마감 시각은 공고에 나와 있지 않아요"라고 쓴다.
- 성적·소득 같은 조건은 "귀띔은 성적을 받지 않아요. 학교 공지에서 직접 확인해 주세요."로 안내한다.
- 저장한 공고의 마감일 변경은 saved_deadline_snapshot과 최신 application_deadline을 비교해 보여 준다. 기준은 최신 값이다.
- 프로필이 없으면(latest) 추천 이유 없이 최신순이며, 홈 첫 카드에서 프로필 입력을 권한다.
- 원문 확인이 24시간을 넘으면 리포트에 '오래된 정보' 안내를 한다(D-006). 마감·삭제된 저장 공고는 상태를 표시한다.

데이터 출처

- 브리핑과 홈은 list_recommendations와 list_saved_notices 응답만으로 앱에서 센다. 앱은 점수를 계산하지 않는다(SPEC §7). 계약 변경은 없다.
- 하루 첫 실행 날짜 저장에 `shared_preferences`(Flutter 공식 패키지, 무료)를 쓴다.

### 이유

- 앱을 열자마자 오늘 볼 것을 정리해 보여 주는 흐름이 "몰랐던 기회 발견"(SPEC §1)에 맞다.
- SPEC §2 범위 안이고 계약을 바꾸지 않는다.
- "확인 필요"와 "마감일 없음"을 숨기지 않는 화면이 데이터 정확성 우선(SPEC §1)을 보여 준다. 다만 거의 모든 공고에 붙는 표시를 경고색으로 칠하면 경고가 의미를 잃으므로 목록에서는 차분하게 보인다.

### 영향

- 앱만 바뀐다: 브리핑 화면 추가, `feed_screen.dart` → 홈, `detail_screen.dart` → 공고 리포트, 테마 색·글꼴 교체. 서버·계약·사전은 바뀌지 않는다.

### 한계·후속

- 홈 목록 카드에는 공고 요약을 넣지 않는다. 목록 응답의 notice_summary에 summary가 없어서다. 넣으려면 계약 변경이 필요하다(AGENTS.md §3).
- 관심사별 건수(예: "AI·데이터 2건")는 목록에 interest_tags가 없어 보여 줄 수 없다. reason_codes 기준 "관심 분야 관련 N건"까지만 보여 준다.
- 조건 불충족으로 추천에서 빠진 공고 수는 응답에 없어서 브리핑에 쓰지 않는다.

## D-010. 어두운 테마와 저장·프로필·로그인 화면

- 상태: **확정** (2026-10-20, 팀장 결정 — 목업 검토 후)

저장한 공고 화면

- 마감된 공고는 "모집이 끝났어요", 학교 공지에서 삭제된 공고는 "학교 공지에서 삭제됐어요"와 "목록에서 지우기" 버튼으로 보인다(SPEC §6).

프로필 화면

- 순서: 학적(학교·학과 선택, 학년 1~4·재학 상태 고르기) → 관심 분야 → 희망 직무 → 저장하기 → 화면(테마) → 계정.
- 관심 분야·희망 직무는 공통 사전의 칩으로 여러 개 고른다. 고른 개수를 보인다.
- 위쪽 말풍선에 "입력한 정보는 추천에만 써요. 성적·학번은 받지 않아요"를 둔다(SPEC §5).
- 계정: Google 계정으로 로그인했다는 것만 보인다. 로그아웃과 탈퇴하기 버튼, "탈퇴하면 프로필과 저장한 공고가 지워져요. 공고 자체는 그대로 남아요."(SPEC §10)

로그인 화면

- 네이비 바탕(다크는 `#0F1222`)에 큰 말풍선 로고, "몰랐던 기회를 먼저 귀띔해 드려요", 앱이 알려 주는 소식 예시 말풍선 3개, "Google 계정으로 시작하기"(D-004), "성적·학번은 묻지 않아요", 이용약관·개인정보 처리방침 동의 문구.
- 소개 문구에서 알림을 약속하지 않는다(푸시 알림은 P0 제외).

## D-014. 포스터 이미지 대체텍스트 읽기 (2026-10-26)

- 상태: **팀장 결정(팀원 확인 전)**
- 근거: 2026-10-26 팀장 지시("이미지 대체텍스트 읽기 붙여서 PR까지 올려. OCR은 보류")
- 배경: 채용·장학 공고 대부분이 포스터 이미지라 마감일과 지원 자격을 읽지 못했다. 학교 편집기는 포스터 이미지에 포스터 글을 옮긴 대체텍스트(alt)를 달아 두는 경우가 많다(2026-10-26 확인: 채용 21건 중 17건, 장학 18건 중 7건, 공지사항 36건 중 0건).

### 결정

- 수집기는 본문(`divMemo`) 이미지의 alt를 본문 끝 `[이미지 설명]` 줄 아래에 붙인다. 20자 미만 alt(제목 정도)는 넣지 않는다. 학교가 쓴 글이므로 다른 본문과 똑같이 원문 근거로 쓴다.
- alt는 ` / `와 문장 끝(한글 뒤 마침표)에서 줄을 나눈다. '접수마감일', '지원자격' 같은 짧은 항목 이름은 다음 값과 한 줄로 둔다(`접수마감일 / 26.12.30(수)`).
- alt가 100자 이상인 이미지는 '읽은 이미지'로 센다(`source_fields.body_image_text_count`, 그런 이미지가 있을 때만 둔다). 지원 조건 완전성은 읽지 못한 이미지가 있을 때만 막는다.
- 두 자리 연도 날짜(`26.12.30(수)`)를 인정한다. 오인을 막으려고 요일이 붙어 있고 실제 달력과 맞을 때만이다. 연도 없는 날짜는 지금처럼 단독으로 인정하지 않는다.
- 분석 `rule-0.4`에서 alt 때문에 드러난 오판을 함께 고친다.
  - '제한 없음'은 대상·자격에 대한 말일 때만 명시적 제한 없음으로 본다('분량 제한 없음'이 "누구나 지원 가능"으로 잡히던 문제).
  - 거주·주민등록·소재·출신·국적 조건은 미해석 조건으로 둔다.
  - 재학생과 복학생·입학예정자·편입생·신입생이 한 줄에 함께 나오면 재학 상태 조건을 만들지 않고 미해석 조건으로 둔다. 휴학 중인 복학 예정자가 잘못 '불충족'이 되지 않게 한다.
- 이미지 OCR(gemma4 비전)은 보류한다. 공지사항 포스터 1장 시험에서 큰 글씨와 마감일은 맞았지만 요일·작은 글씨를 틀리고 없는 문장을 만들었다(한 장 18초).

### 이유

- alt는 학교가 직접 쓴 글이라 원문 근거 검증(SPEC §6 수집·분석 5)을 그대로 적용할 수 있다. OCR 결과는 원문처럼 믿을 수 없다.
- 새 의존성·비용이 없다.

### 영향

- 수집기: `parser.py`, `adapter.py`. 분석: `dates.py`, `rules.py`(`rule-0.4`). 계약은 `body_text` 설명만 고쳤다(`raw_notice.schema.json`, SPEC §5). 구조·`schema_version`은 그대로다.
- alt가 붙는 공고는 본문이 바뀌므로 다음 배치에서 한 번 수정본(notice_version +1)으로 들어온다. alt가 없거나 짧은 공고는 content_hash가 그대로다.
- API·앱은 바뀌지 않는다. 배포 없이 `Gwittim-batch` 갱신만 필요하다.

### 한계·후속

- 공지사항 포스터에는 alt가 없다. 다만 본문에 같은 내용이 글로 있는 경우가 많았다.

## D-015. 체크리스트 조건 정리와 우대 사항 구분 (2026-10-27)

- 상태: **팀장 결정(팀원 확인 전)**
- 근거: 2026-10-27 팀장 지시("중복·제목 줄 정리, 자격/우대 나누기, 형광펜 빼기, 3개 넘으면 접기까지 해서 PR 올려")
- 배경: 채용 공고 리포트의 '직접 확인'이 14개까지 나왔다. 본문과 이미지 대체텍스트에 같은 조건이 있어 두 번씩 나오고, '2. 지원자격 및 우대사항' 같은 제목 줄과 '○', '우대사항 /' 앞머리가 그대로 보였다. 필수 자격과 우대 사항이 섞여 있었고, 24자 이하 줄에만 형광펜이 칠해져 들쭉날쭉했다.

### 결정

분석 `rule-0.6`

- 미해석 조건 문구에서 앞의 번호·기호(`2.`, `○`, `·`, `-`, `/` 등)와 항목 이름(`우대사항 /`, `우대사항:`, `공통 /`)을 뗀다. 뗀 문구도 원문 줄의 일부라 근거 검증을 그대로 통과한다.
- 항목 이름만 있는 줄('지원자격 및 우대사항', '자격요건')과 '우대사항: 없음'은 조건으로 넣지 않는다. 그런 줄이 있었으면 그 아래 조건을 다 읽었다고 볼 수 없어 지원 조건 완전성은 false로 둔다.
- 공백을 뺀 문구가 같은 조건은 하나만 남긴다. 규칙 결과와 LLM 결과를 합친 뒤에도 한 번 더 정리한다.
- 아래 경우 `note`를 '우대 사항'으로 둔다. 판정 규칙은 바꾸지 않고 보여 주는 방식만 바꾼다.
  - 항목 이름이 우대인 경우
  - 문구가 '…우대'로 끝나는 경우
  - 원문의 '우대사항' 항목 아래 줄인 경우. 다음 번호 제목, 필수 요건, 이미지 설명이 나오면 항목이 끝난다.
- '필수', '자격요건:'이 들어간 줄과 '우대가점', '우대사항은 … 충족' 같은 문장은 우대 사항이 아니다.

앱

- 우대 사항은 지원 자격 뒤에 '우대 사항 N개'로 따로 묶는다. 회색 상자와 '갖추면 유리한 조건이에요.'로 보이고, '○개 조건은 직접 확인해 주세요'의 개수에는 넣지 않는다.
- 묶인 근거는 형광펜 없이 점 목록으로 보인다. 3개를 넘으면 처음 3개만 보이고 '○개 더 보기'로 펼친다.

### 이유

- 같은 조건이 반복되고 제목·기호가 섞이면 무엇을 확인해야 하는지 읽기 어렵다.
- 우대 사항은 없어도 지원할 수 있어서, 필수 자격과 같은 무게로 보이면 지원을 망설이게 만든다.

### 영향

- 분석: `rules.py`(`tidy_unresolved`, `rule-0.6`), `llm.py`. 계약은 `unresolved_condition.note` 설명만 고쳤다(`common.schema.json`). 구조·`schema_version`은 그대로다.

- 다음 배치가 모든 공고를 다시 분석한다.

### 한계

- 한 줄에 조건 두 개가 붙어 있으면('교대근무 가능자 / · 화공… 우대') 나누지 못한다.

## D-018. 브리핑은 조건이 맞을 때만 나오는 소식으로, 머리는 네이비 (2026-10-29)

- 상태: **팀장 결정(팀원 확인 전)**
- 근거: 2026-10-29 화면 피드백 검토 후 팀장 지시("진행")

5. 저장한 공고 마감 변경: 그대로.

- 맞춤 공고 전체 목록('관련 공고 N건')은 브리핑에서 뺐다. 홈 '나에게 맞는 공고'와 공고 탭에 있다.

## D-019. 카카오톡 알림톡 출처와 알림톡 분류 모델 (2026-10-30)

- 상태: **팀장 결정(팀원 확인 전)**
- 근거: 2026-10-30 팀장 지시("멘토링 받은거니 범위 확장하고 P0에서 붙여보자")
- 배경: 멘토링(10/29)에서 "규칙 기반과 AI 결과 차이를 모르겠다"는 지적을 받고, 학교 카톡 알림톡으로 분류 모델을 직접 학습해 규칙·Gemma와 비교했다(`localModel/`). 알림톡은 www 게시판에 없는 비교과·특강·어학 안내가 많지만 앱에는 연결되지 않았다.

### 결정

SPEC 범위 변경 (AGENTS.md §3, SPEC 0.4)

- 새 출처 `mjc_kakao`: 팀장 PC 카톡에서 학교 채널 6개(공지사항·교수학습지원·원격교육지원센터·상담센터·스마트케어·글로벌교육센터) 대화를 내보낸 txt를 수동으로 넣는다. 실행은 `uv run python -m backend.collectors.mjc_kakao --export-dir <폴더>`이고 자동 수신은 하지 않는다.
- 게시는 공통 공지(broadcast)만 한다. 수강 과목 알림, 이름·학번이 든 개인 결과, 신청한 학생에게만 온 운영 안내(participant), 채널 자동응답은 게시하지 않는다. 받은 사람의 '내 알림함'은 P0 제외다.
- 본문은 학번·휴대폰·교수 이름·수신자 이름을 가린 글을 쓴다. 같은 방에서 45일 안에 거의 같은 글(글자 3-gram 유사도 0.8 이상)이 다시 오면 한 공고로 묶는다. 공고 ID는 묶음 첫 메시지(방·발송 시각·본문)의 해시라서, 나중에 다시 내보내도 바뀌지 않는다.
- 게시일은 첫 발송 시각이다(분 단위, `Asia/Seoul`). 근거는 `backend/sources.py`에 남겼다.
- 전처리 코드는 `backend/collectors/mjc_kakao/parser.py` 하나다. 학습(`localModel/kakao_preprocess.py`)도 이 코드를 불러서, 모델이 배운 입력과 서비스 입력이 같다.

계약 (`schema_version` 1.0 유지, 하위 호환)

- `RawNotice.source_url`, `Notice.source_url`, 목록의 `notice_summary.source_url`이 null일 수 있다. 웹 원문이 없는 출처만 해당하고, 이때 `source_notice_id`가 필수다. 기존 게시판 공고는 그대로 URL이 있다.

분석 (알림톡만, 분석 버전 `<기존>+kakao-0.1+kdate-0.1`)

- 날짜·지원 조건·요약은 기존 분석기(규칙 + gemma4 보강)를 그대로 쓴다.
- 알림톡 날짜 보강(`kdate-0.1`, `backend/analysis/kakao.py`): 알림톡은 '9월 11일(금)까지', '10/7(수) 17:00까지'처럼 연도를 거의 쓰지 않아 기존 분석기가 날짜를 버린다. 기존 분석기가 비워 둔 칸만 다시 읽는다.
  - 연도: 발송일 앞 60일 ~ 뒤 240일 안에 오는 해. 요일이 붙으면 달력과 맞아야 한다. 점·빗금 날짜(10/7)는 요일·'까지'·시각이 붙을 때만 날짜로 본다.
  - 신청 마감: '까지'·'마감'·'신청 기간' 줄의 날짜 중 가장 늦은 날짜. 여러 프로그램을 묶은 안내가 많아 앞 프로그램 마감으로 닫히지 않게 한다.
  - 활동 기간: 그 밖의 날짜(특강·검사·행사일)의 처음 ~ 마지막.
- 끝난 공고: 마감일이 없으면 활동 기간의 마지막 날짜가 지났을 때 `closed`다(`backend/analysis/notice.py`의 `ACTIVITY_CLOSES`). 게시판 공고에는 쓰지 않는다.
- 제목: 첫 줄이 인사·부서 소개('명지전문대학 원격교육지원센터입니다.')·발송 안내면 건너뛴다(`parser.title_of`). 학습 전처리도 같은 함수를 쓰므로 다음 학습부터 반영된다. 지금 모델은 다시 학습하지 않았다.
- 게시 범위: 대화 내보내기에는 몇 달 치 지난 알림톡이 들어 있다. 이미 끝난 공고(`closed`, 마감 미상으로 60일 지난 공고)는 처음부터 게시하지 않는다. 한 번 게시한 공고는 끝나도 `closed`로 갱신해 게시한다(`run_kakao`). 로컬 기록에는 모두 남아 학습에 쓴다.
- 카테고리와 관심사는 알림톡으로 학습한 모델이 붙인다. 관심사 모델은 글자 단위, 임베딩, 평균 풀링, sigmoid이고 꼬리표 3개와 '기타'를 낸다. 카테고리 모델은 글자 단위, 임베딩, 평균 풀링, softmax이며 게시판 공고 132건을 학습에 보탰다.
- 다음 경우에는 애매하다고 보고 gemma4에 같은 분류 프롬프트로 다시 묻는다(캐스케이드).
  - 모델이 '기타'라고 볼 때 (`기타 확률 ≥ 0.15`)
  - 꼬리표 확률이 문턱 0.2 ± 0.05 안일 때
- Gemma가 꺼져 있거나 실패하면 모델 결과로 게시한다. 이때 분석 버전에 `-nogemma`를 붙여 다음 실행 때 다시 분석한다.
- 행정 공지(`admin_notice`)로 분류되면 꼬리표를 붙이지 않는다(SPEC §6 추천 1).
- 게시판 공고(`mjc_www_*`)의 꼬리표는 지금처럼 키워드 규칙이다(D-008). 모델은 알림톡으로만 학습·평가했다.
- 추천 점수·순위는 바뀌지 않는다(`rank-0.3`). 모델은 꼬리표만 붙이고, 점수는 SPEC §6 규칙으로 계산한다.

모델 배포

- TensorFlow는 학습 환경(`localModel/.venv`)에만 둔다. `localModel/export_weights.py`가 가중치와 글자 목록만 `backend/classifier/models/`로 꺼낸다(두 모델 합쳐 약 0.4MB). 배치는 `backend/classifier/text_model.py`가 표준 라이브러리로 같은 계산을 한다. 서버·배치에 새 라이브러리는 없다.
- 글자 단위 모델만 내보낸다. 단어 단위 단어장에는 공지 속 담당자 이름·이메일이 단어로 남아 저장소에 올릴 수 없다. 카테고리는 단어 단위(정확도 0.66) 대신 글자 단위(0.64, 47건 중 1건 차이)를 쓴다.

앱

- 출처 이름 '명지전문대 카카오톡 알림톡'과 '○월 ○일 HH:MM 발송'을 보여 준다.
- 원문 링크가 없으면 '학교 공지에서 보기' 버튼 대신 "카카오톡 알림톡으로 받은 공지라 원문 링크가 없어요."를 보여 준다.
- 알림톡은 보낸 뒤 바뀌지 않으므로 '마지막 확인 ○일 전' 안내를 하지 않는다.

### 이유

- 교수님 지적에 답하려면 규칙과 AI의 차이가 숫자뿐 아니라 실제 앱 추천에서도 보여야 한다.
- 알림톡은 학생 대부분이 받지만 읽지 않고 넘기는 정보다. 관심사 꼬리표가 붙으면 관심 있는 학생 쪽으로 순서가 올라간다. 다른 학생에게서 숨기지는 않는다.
- 사람 검수 47건 기준 성적
  - 관심사(배운 꼬리표 3개): 모델 F1 0.77, 규칙 0.67, Gemma만 0.75
  - 관심사(꼬리표 18개 전체): 캐스케이드 F1 0.68로 Gemma만 쓸 때와 같다. Gemma 호출은 26%뿐이다.
  - 카테고리 정확도: 모델(글자 단위) 0.64, 규칙 0.40, Gemma 0.60
- 학습 코드와 평가는 `localModel/`과 `Claude outputs/귀띔_알림톡모델_코드설명.md`(저장소 밖 설명 자료)에 있다.

  - 분류: `backend/classifier/`(새로 만듦), `backend/analysis/kakao.py`

### 한계·후속

- 알림톡은 수동 내보내기라 새 알림이 바로 들어오지 않는다.
- 날짜가 아예 없는 안내(설문 링크, 이용 안내)가 있다. 이런 공고는 60일 규칙(D-013)으로만 빠진다.
- 연도 없는 날짜의 해는 발송일로 정한 추정이다. 요일이 붙은 날짜는 달력으로 확인되지만, 요일 없는 '9월 16일'은 발송일 근처라는 근거뿐이다.
- 모델이 배운 관심사는 3개(AI·데이터, 외국어, 미디어)뿐이다. 나머지는 '기타'로 알아채고 Gemma에 넘긴다. 시험 세트는 47건으로 작다.
- 게시판 공고로 관심사 학습을 보강해 봤지만 효과가 없어 앱 모델은 그대로 둔다 (2026-10-30, 아래 표).
  - 게시판 4곳의 지난 공고를 10페이지씩 한 번 모으고(`localModel/board_history.py`, 516건, 앱·Firestore에는 넣지 않음), Gemma로 라벨을 붙였다(실패 0).
  - 꼬리표 16개를 배웠지만 알림톡 시험 세트 성적은 떨어졌다. 장학·채용·근로 공고가 많아 알림톡과 꼬리표 분포가 다르고, 게시판 쪽이 학습 데이터의 대부분을 차지하기 때문으로 본다.
  - 알림톡을 늘리거나(같은 반 팀원 내보내기는 같은 방이라 중복이 대부분) 알림톡 사람 검수를 늘리는 쪽이 다음 후보다.

  F1은 사전의 관심사 코드 전체로 채점했다(모델이 못 배운 꼬리표도 놓침으로 셈). 가중치 0.3·0.5도 0.1보다 나빴다.

## D-020. 학과 통계 보조 점수와 프로필 학과 통계 칩 (2026-10-30)

- 상태: **팀장 결정(팀원 확인 전)**
- 근거: 2026-10-30 팀장 지시("멘토링 받은거니 범위 확장하고 P0에서 붙여보자", "통계 추천 먼저")
- 배경: 멘토링(10/29) 목표 2 "학과나 관심사, 희망 직종 같은 걸로 통계를 찾아봐서 보통 이런 사람들은 ~ 많이 하는구나 해서 자동 추천". 관심사·직무를 고르지 않고 학과만 입력한 학생은 학과 꼬리표가 붙은 공고가 적어 추천이 거의 개인화되지 않았다. 실험(`Claude outputs/목표2_학과통계추천/`)에서 공개 통계로 만든 학과 사전 확률을 약한 점수로 더하는 방식(A)을 골랐다.

### 결정

통계표 `contracts/stats/major_prior.json` (스키마 `contracts/major_prior.schema.json`)

- 학과 31개(자유전공 제외)마다 P(직무 | 학과), P(관심사 | 학과)를 둔다.
- 커리어넷 학과정보의 두 자료로 계산한다(`tools/build_major_prior.py`).
  - 졸업 후 첫 직업분야 비율: 한국고용정보원 대졸자 직업이동 경로조사 2020, 직업 대분류 10개, 계열 단위
  - 관련직업 목록: 학과마다 2~22개
- mjc 학과는 이름이 같거나 가장 가까운 커리어넷 학과에 대응했다. 경영·행정·커뮤니케이션디자인은 4년제 학과로 대응했다.
- 커리어넷 학과정보 글은 공공누리 제4유형(출처 표시·비상업·변경 금지)이다. 옮겨 적은 원자료(`data/careernet_majors.json`)는 저장소·앱에 싣지 않고, 계산한 확률만 출처와 함께 싣는다.

추천 `rank-0.4`

- 점수 요소 `major_prior`(가중치 20)를 더한다. 학과를 입력한 모든 학생에게 평가한다(관심사·직무를 고른 학생 포함, 2026-10-30 팀장 지시 "학과 선택만 한거 말고도 다 쓰면 좋겠는데").
- 값 = 공고 꼬리표 중 가장 잘 맞는 하나의 학과 확률 ÷ 그 학과의 가장 큰 확률. 직무·관심사 중 큰 쪽을 쓴다. 꼬리표를 많이 단 공고가 유리해지지 않게 합이 아니라 최댓값을 쓴다.
- 값이 0.5 이상이면 추천 이유 `major_prior_match`를 붙인다.
- 프로필에는 아무것도 쓰지 않는다. 학생 정보를 추정해 확정하지 않는다.

계약

- `recommendation_item.reason_codes`에 `major_prior_match`를 더했다. latest 모드 제약은 그대로다. `schema_version`은 1.0을 유지한다(값 하나 추가, 기존 응답은 그대로 유효).
- 샘플: `fixtures/valid/user_profile/major_only`, `fixtures/valid/recommendation_list_response/major_only`
- `tools/validate_contracts.py`가 통계표의 스키마, 사전 코드, 확률 합을 확인한다.

앱

- 추천 이유: "학과 졸업생 진로와 관련 있어요." 리포트에는 "학과 졸업생 진로는 커리어넷 학과정보 통계(2020 조사)로 계산했어요."를 덧붙인다. 목록 카드는 "같은 학과 졸업생이 많이 가는 분야의 공고예요".
- 프로필 고치기 2단계(관심 분야): 학과를 골랐으면 위에 "○○학과 졸업생은 이런 분야로 많이 가요" 말풍선과 칩 3개를 보이고, 아래에 '전체 분야'를 둔다. 미리 고르지 않는다. 학생이 눌러야 저장된다.
- 통계표 사본은 `apps/mobile/assets/stats/major_prior.json`(`tools/export_mobile_sample.py`가 복사).

### 이유

- 학과만 입력한 학생에게도 "보통 이 학과 학생은 ~"이라는 근거로 순서를 매길 수 있다.
- 통계 점수(20)는 직접 고른 관심사(40)·직무(35)보다 약하다. 고른 분야와 맞는 공고가 앞서고, 같은 조건의 공고 사이에서 학과 졸업생이 많이 가는 분야가 앞선다. 학생이 직접 말한 것을 통계가 덮지 않는다.
- 칩은 학생이 확정하는 방식이라 사용자 정보를 추정해 저장하지 않는다.

### 영향

- 백엔드: `backend/recommendation/`(`major_prior.py`, `config.py`, `scoring.py`, `ranking.py`). API는 같은 응답 형식이고 Cloud Run 이미지에 `contracts/`가 이미 들어간다. 반영하려면 API를 다시 배포해야 한다.
- 앱: 새 빌드가 필요하다. 예전 빌드는 `major_prior_match`를 모르는 코드로 보고 문구를 비워 두지만 다른 이유는 그대로 보인다.
- 관심사·직무를 고른 학생도 순위가 조금 바뀐다. 고른 분야와 맞는 공고가 맞지 않는 공고보다 앞서는 것은 테스트로 확인했다.

### 한계·후속

- 통계가 계열 단위·2020년 조사라 학과 차이가 실제보다 작고 오래됐다. 명지전문대 졸업생 실측이 아니다.
- 관련직업 목록 편향: 행정학과는 세무·회계가 사무보다 크고, 컴퓨터보안과는 기계 직무가 크다. 직무 사전에 스포츠·미용이 없어 사회체육과는 예술·공연, 미용과는 서비스로 간다.
- 마감 임박 점수(10)가 통계 점수보다 세게 작동하는 경우가 있다(컴퓨터공학과에 마감 임박한 보험 채용이 위로). 마감 시기 점수를 개인화 요소가 맞을 때만 더할지는 따로 정한다.
- 커리어넷 웹 페이지에서 옮겨 적은 자료다. 공식 Open API 인증키를 받으면 같은 스크립트로 다시 만든다.

## D-021. 학과 통계 추천은 표시를 붙여 따로, 관심 있음·없음으로 계속 보일지 정함 (2026-10-30)

- 상태: **팀장 결정(팀원 확인 전)**
- 근거: 2026-10-30 팀장 지시("마감 임박에서 같이 띄우는 대신 통계 기반 추천 공고는 안내표시랑 같이 뜨게 해줘. 또 우리가 강제로 띄우는 추천인만큼 관심있음, 관심없음 같은 버튼으로 사용자가 이걸 실제로 원하는지 알아서 계속 띄울지 그만 띄울지도 판단해")
- 배경: D-020에서 학과 통계 점수를 모든 학생에게 켜자, 앱이 추천 이유(`major_prior_match`)가 있는 공고를 '관련 공고'로 보면서 D-016(마감 임박은 관련 공고에서만)의 마감 임박·새 공고·다가오는 마감에 학생이 고르지 않은 분야 공고가 섞였다.

### 결정

- '관련 공고'는 학생이 고른 관심 분야·희망 직무·전공 이유(`interest_match`, `role_match`, `major_match`)가 있는 공고만이다. 학과 통계 이유만 있는 공고는 '학과 통계 추천'이다.
- 브리핑: 학과 통계 추천 중 7일 안 마감이 가장 가까운 공고 하나를 따로 보인다.
  - 카드 위에 '학과 통계 추천' 표시, "직접 고른 분야는 아니지만, 같은 학과 졸업생이 많이 가는 분야의 공고입니다.", 출처(커리어넷 학과정보 통계 2020)를 붙인다.
  - '이런 추천을 계속 받으시겠습니까?' 아래 '관심 있음'·'관심 없음' 버튼. 답한 공고는 브리핑에 다시 나오지 않는다.
  - 머리 배지와 홈 오늘의 귀띔 카드에 '학과 통계 추천' 배지.
- 홈 다가오는 마감(2주): 학과 통계 추천도 넣되 제목 위에 '학과 통계 추천' 표시. '관심 없음'이라고 답한 공고는 뺀다.
- 계속 보일지 판단(학습이 아니라 정해진 규칙, `MajorPickState`):
  - '관심 없음'이 3번 이어지면 30일 동안 학과 통계 추천을 보이지 않는다. '관심 있음'은 이어진 수를 0으로 되돌린다.
  - 30일이 지나면 다시 보인다. 프로필 학과를 바꾸면 이전 답을 버리고 처음부터 본다.
- 답은 기기(SharedPreferences, 브리핑 기록과 같은 곳)에만 남기고 서버에 보내지 않는다. 계약·API는 바뀌지 않는다.
- 공고 목록 순서(서버 점수)는 그대로다. 답은 브리핑·홈의 표시만 바꾼다.

### 이유

- 학생이 고르지 않은 분야를 앱이 먼저 권하는 것이라, 고른 분야 공고와 구분해 보여야 학생이 왜 나왔는지 안다.
- 원하지 않는 학생에게 계속 보이면 소음이 된다. 몇 번 답하면 알아서 멈추고, 학과가 바뀌거나 시간이 지나면 다시 기회를 준다.
- 기기에만 남기면 계약·서버를 바꾸지 않고 P0 안에서 끝난다. SPEC P0 제외의 '피드백 가중치 학습'과 달리 점수·순위를 학습하지 않는다.

### 영향

- 앱: `briefing_data.dart`(`chosenReasons`, `isMajorPick`, `majorPicks`, `MajorPickState`, `BriefingStore` 확장), `briefing_screen.dart`(학과 통계 추천 카드, `MajorPickLabel`), `home_screen.dart`(다가오는 마감 표시, 답 저장).
- 서버·계약: 바뀌지 않는다. 학과 통계 추천이 실제로 나오려면 D-020 반영(API 다시 배포)이 먼저다.

### 한계·후속

- 답이 기기에만 있어 다른 기기·재설치에서는 처음부터다. 학과 통계 추천의 실제 반응을 모아 평가하려면 서버에 답을 보내는 계약 변경이 필요하다(개인정보 검토 포함).
- '관심 있음'을 프로필 관심 분야로 옮기는 버튼은 넣지 않았다.
- 공고 리포트·공고 탭·달력에서는 답 버튼을 보이지 않는다(브리핑에서만 묻는다).

### 확인

- `flutter analyze`: 문제 0개 / `flutter test`: 121건 통과, 2건 건너뜀 (새 테스트: 브리핑 분리·답한 공고 제외, 3번 이어진 '관심 없음'·30일·학과 변경, 카드 표시와 답)
- 임시 웹 빌드(모바일 크기)로 브리핑 카드에 표시·문구·버튼이 나오는 것을 봤다. 캡처 오른쪽이 잘려 줄바꿈·여백 확인은 불완전하고, 실기기 확인은 아직이다.

## D-022. 앱 문구 말투: 해요체 대신 명사형과 합쇼체 (2026-10-30)

### 결정

- 앱 문구에서 해요체(~요)를 뺀다. 배지·칩·카드 한 줄·제목은 명사형, 짧은 결과 알림과 안내 문장은 합쇼체로 쓴다. 자세한 규칙은 `ui-style.md` §2 문구에 있다.
- 로그인 소개 문구를 "귀띔이 맞춤 공고를 먼저 안내해 드립니다"로 바꾼다(D-010의 "몰랐던 기회를 먼저 귀띔해 드려요" 대체). '가장 먼저'는 수집 주기상 지킬 수 없어 넣지 않는다. 알림은 여전히 약속하지 않는다.
- 조건 결과는 '충족 / 미충족 / 확인 필요'로 통일한다(기존 '맞아요', '맞지 않아요', '불충족').
- 남은 기간은 'D-N' / '오늘 마감', 마감 변경은 '마감 N일 연장 / 단축'으로 쓴다.
- 주의 문구는 뜻을 바꾸지 않는다: "관심사·희망 직무·전공·마감 시기로 정한 순서입니다. 합격 가능성과는 관계없습니다."(D-009)

### 이유

- 해요체가 흔한 AI 생성 문구처럼 보여 팀장이 바꾸기로 했다.
- 정보 앱이라 상태는 짧은 명사형이 읽기 빠르고, 안내는 합쇼체가 단정하다.

## D-023. 지원 자격 거르기 강화: LLM 확인 항목은 신청자 본인 조건만 (2026-10-31)

- 상태: **팀장 지시(팀원 확인 전)**
- 근거: 2026-10-31 팀장 지적("자격 요건 필터링이 약한 것 같음. 둘이 중복돼")
- 배경: 프레젠테이션 경진대회 리포트에서 '재학 상태: 재학'이 충족인데, 같은 줄의 '개인 또는 팀(2명 이하)'와 공모 주제 '지정주제 중 택 1'이 '직접 확인'으로 또 나왔다. 저장된 공고 425건의 LLM 확인 항목 579개를 보니 대부분 일정·혜택·제출 방법·팀 구성·대상 설명이었다. 규칙은 '휴학생 및 정규학기를 초과한 학기의 재학생은 추천 불가'를 재학·휴학 허용으로 읽어 휴학생에게 충족으로 보일 수 있었다.

### 결정

분석 `rule-0.7`

- LLM이 낸 확인 항목(`unresolved`)은 신청자 본인 조건일 때만 받는다(`is_llm_condition`).
  - 받는 것: 성적·이수 학점, 소득·학자금 지원구간, 나이, 거주·주민등록, 국적·유학생, 어학 점수·자격증·면허, 장애·보훈 등 대상 구분, 재직·직계, 경력·근무 가능, 중복 수혜 불가, 학적 변동.
  - 학년·재학·졸업·전공심화 문구는 이미 조건으로 읽은 줄의 일부가 아닐 때만 받는다.
  - 원문 '우대사항' 항목 아래 줄은 낱말과 관계없이 받는다. 우대 사항으로 따로 묶여 확인 필요 수에 들지 않는다(D-015).
  - 빼는 것: 팀 구성, 혜택(마일리지 등), 제출·준비·안내 문장, '…포함'·'…가능'처럼 대상을 넓히는 말(제한을 함께 말하면 받음), 규칙이 이미 낸 줄의 일부.
- LLM 프롬프트에도 확인 항목에 넣을 것(자격·우대 조건)과 넣지 말 것을 적었다. 프롬프트는 보조이고 거르기는 코드가 한다.
- 학적·학년·학과를 '불가·제외'하는 줄은 조건으로 만들지 않고 직접 확인으로 둔다. LLM 조건도 같은 줄이면 버린다.
- 규칙의 확인 항목에서 혜택·마일리지·출결·성적 조회 안내 줄을 뺀다.
- '재·휴학생'은 재학생과 휴학생으로 읽는다. 이전에는 휴학생만으로 읽어 재학생에게 미충족이 됐다(IR챌린지 공고 1건).
- '고등학교 졸업자', '고등학교 졸업 이상' 같은 고졸 이상 학력 줄은 재학·휴학·졸업 모두로 읽는다. 대학생은 모두 고졸 이상이다. 이전에는 같은 줄의 '졸업자'만 보고 졸업생만으로 읽어 재학생에게 미충족이 됐다(S-OIL·KB손해보험 채용 2건). 제출 서류 줄과 '고등학교 졸업예정자'는 해당하지 않는다.

### 이유

- 이미 충족으로 판정한 줄을 다시 묻거나 자격이 아닌 말을 확인하라고 하면 체크리스트를 믿기 어렵다.
- 빼는 조건을 허용으로 읽으면 판정이 뒤집힌다. 모르는 것은 확인 필요로 두는 쪽이 맞다(SPEC 데이터 정확성).

### 영향

- 분석: `rules.py`, `llm.py`. 계약·앱·`schema_version` 변경 없음.
- 다음 배치가 모든 공고를 다시 분석한다(LLM 포함).
- 근로장학 공고 9건의 재학 상태 조건이 '직접 확인'으로 바뀐다. 이 중 3건은 이전에 '휴학생만'으로 판정돼 있었다.

### 한계

### 확인

## D-024. 첫 로그인 프로필 안내와 탈퇴 (2026-10-31)

### 결정

- 로그인 모드에서 서버에 프로필이 없으면 홈을 처음 받은 뒤 안내 화면("맞춤 공고를 위해 몇 가지만 묻습니다", 세 단계·성적·학번 안 물음·나중에 고칠 수 있음, '시작하기'·'나중에 입력')을 띄우고, '시작하기'로 프로필 입력 세 단계(학적 → 관심 분야 → 희망 직무)에 들어간다. 첫 단계에서 뒤로 가면 안내 화면으로 돌아간다. 브리핑보다 먼저 띄우고, 닫으면 홈의 '프로필 입력' 카드로 다시 연다. 프로필을 읽지 못하면(미상) 띄우지 않는다. 샘플·개발 토큰 모드에서는 띄우지 않는다.
- SPEC §7에 `delete_account_data`를 추가한다. HTTP는 이미 있던 `DELETE /v1/profile`(204, 반복 요청 안전)이다. 프로필·저장을 지우고 공개 공고는 남긴다.

### 이유

- 첫 로그인 사용자가 프로필 없이 최신순 목록만 보고 지나치지 않게 한다.

- Firebase 계정 삭제는 최근 로그인을 요구해서, 데이터를 지우기 전에 재인증을 받아야 "데이터는 지웠는데 계정은 남는" 경우가 줄어든다.

### 영향

- 계약: SPEC §7 인터페이스 한 줄 추가. JSON Schema·`schema_version`·fixtures 변경 없음(응답 본문 없음).
- 서버: 변경 없음. `DELETE /v1/profile`과 테스트(`test_account_deletion_removes_profile_and_saved`)는 W13부터 있었고, 배포된 dev 서버에도 경로가 있다(토큰 없이 401).

- 한계: 서버 삭제 뒤 Firebase 계정 삭제가 실패하면 데이터만 지워진 채 로그인 상태로 남는다. 탈퇴를 다시 누르면 된다(서버 삭제는 반복 요청 안전). 개인정보 처리방침 문서는 아직 없다(D-010 한계).

## D-025. 알림톡과 게시판 공고 짝 찾기, 신청 사이트 (2026-11-01)

- 상태: **팀장 지시(팀원 확인 전)**

### 결정

알림톡 배치 (`backend/analysis/kakao_match.py`, 분석 버전에 `+kmatch-0.1`)

- 관련 공고: 게시판 공고 제목의 핵심 낱말(머리말·연도·'안내·모집' 같은 흔한 말 뺌)이 알림톡 제목+본문에 75% 이상, 2개 이상 있고, 게시판 공고가 알림톡보다 45일 앞 ~ 7일 뒤에 올라왔으면 관련 공고다. 최대 3개를 `related_notices`로 붙인다.
- 같은 공고: 거꾸로 알림톡 제목의 핵심 낱말이 관련 공고들 제목에 70% 이상 있으면 같은 공고로 보고 알림톡을 게시하지 않는다(이미 게시했으면 내린다). 게시판 공고에 원문 링크와 자세한 조건이 있다.
  - 'AI 카드뉴스'처럼 알림톡에만 있는 말이 제목에 남은 묶음 안내는 게시하고 관련 공고를 붙인다.
- 신청 사이트: 알림톡 본문에 처음 나오는 학교 사이트 주소(`*.mjc.ac.kr`, 스마트케어 `mpu.mjc.ac.kr` 등)를 `apply_url`로 붙인다. 사이트는 수집하지 않고 앱에서 열기만 한다. Zoom 등 학교 밖 주소는 붙이지 않는다.
- 게시판 공고 기준이라 게시판 배치 뒤에 알림톡 배치를 실행한다. 원문·분석이 그대로여도 관련 공고가 바뀌면 다시 게시한다(`publisher._same`).

계약 (`schema_version` 1.0 유지, 하위 호환)

- Notice 선택 필드 `apply_url`(string 또는 null), `related_notices`(`{notice_id, title}` 배열, 최대 3개). 게시판 공고에는 없다.

앱

## D-026. 공고 탭 검색·분류 칩 (2026-11-01)

- 상태: **팀장 지시(팀원 확인 전)**
- 근거: 2026-11-01 팀장 요청("공고 탭쪽 공고 성격별로 분류할 수 있는 칩", "기본적으론 추천순이니 모두 보여주고 아래로 살짝 당기면 검색이랑 분류칩", "새 api 배포 오래걸리는거 아니면 이참에 다해두자")
- 배경: 2026-10-25 Q1 B에서 공고 탭은 '나에게 맞는 공고' 목록만 두고 검색·필터를 넣지 않기로 했다. 앱은 추천 상위 20건만 받아서, 앱 안에서만 거르면 분류마다 1~6건밖에 안 됐다.

### 결정

- 공고 탭: 기본은 지금처럼 추천순 전체 목록. 목록을 조금 끌어내리면 '나에게 맞는 공고' 제목이 사라지며 같은 자리에 검색·분류 칩이 나온다. 맨 위에서 더 끌어내리면 새로 고침이다(Q1 B의 '검색·필터 없음'을 바꾼다).
  - 처음 만든 모양(머리 위 큰 검색 칸 + 알약 칩)은 팀장이 '촌스럽다'고 해 같은 날 바꿨다(2026-11-01): 칩은 공고 카드 같은 둥근 사각형, 검색은 칩 줄 첫 칸 '검색'을 누르면 그 자리에 검색 칸이 뜬다.
  - 그다음 '당기면 제목이 칩으로 바뀌는' 숨김 방식은 새로 고침과 같은 당김을 나눠 써서 새로 고침이 안 되거나 칩이 갑자기 뜨는 문제가 났다. 팀장 결정으로 칩 줄을 제목 아래에 늘 두고, 당기면 새로 고침만 하게 했다(같은 날, #63).
  - 칩 줄 때문에 보이는 공고가 줄어드는 대신 공고 카드를 단순화했다: 분류 옆에 마감을 두고 따로 있던 마감 줄을 뺐다. 조건 충족 체크는 추천 이유 앞에서 빼고 오른쪽 칩('조건 충족')으로 옮겼다(체크가 '관심 분야 연관'의 강약처럼 읽혔다).
- 서버: `GET /v1/recommendations`에 선택 입력 `q`(50자 이내), `category`(공통 분류 코드, 모르는 코드는 invalid_argument). 추천 후보 중 제목·요약에 `q`가 든 공고(띄어쓰기·대소문자 무시), 그 분류 공고만 돌려준다. 제외 규칙(마감·검토 대기·not_met·행정 공지·오래된 마감 미상)과 순서는 추천과 같다(`backend/recommendation/ranking.py`의 `matches`).
- 앱: 저장소에 `searchNotices(query, category)`. 추천 목록은 50건(서버 최대)씩 받는다. 검색은 입력이 멈추고 0.35초 뒤 보내고, 늦게 온 이전 응답은 버린다. 검색 결과는 탭끼리 나눠 쓰지 않는다(#60 `CachedNoticeRepository`).
- 분류 칩은 공통 분류 사전 순서('전체' + 12개, 행정 공지 제외). 고른 칩은 하나만이다.

### 이유

- 추천순은 그대로 두고 필요할 때만 꺼내 쓰게 하면 처음 화면이 복잡해지지 않는다.
- 받아 둔 목록 안에서만 거르면 분류·검색 결과가 너무 적다. 서버는 이미 공고를 다 읽어 추천을 계산하므로 거르는 조건만 더하면 된다.

### 영향

- 서버: `backend/api/app.py`, `backend/recommendation/ranking.py`. 응답 계약은 그대로다. 병합 후 API를 다시 배포해야 검색이 동작한다.
- 앱: `lib/data/*_repository.dart`, `lib/ui/notices_screen.dart`. 추천 목록이 50건이 되어 달력의 마감 표시와 브리핑 건수가 늘 수 있다.
