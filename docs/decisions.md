# 결정 기록 (decisions)

SPEC·역할·기술·계약에 관한 팀 합의를 날짜순으로 남깁니다 (SPEC §12).

- 기록 형식: 번호, 상태, 날짜, 참여자, 결정, 이유, 담당, 영향, 보류 항목, 확인
- 상태 값: `합의안`(검토 전 제안) → `팀장 결정`(팀장 확인, 팀원 확인 전) → `확정`(팀장·팀원 확인 완료) / `보류` / `폐기`
- `팀장 결정` 항목은 작업 기준으로 사용하되, 팀원 의견이 다르면 다시 논의합니다.
- `확정`은 양측이 아래 확인란을 채운 뒤에만 기록합니다. 문서 작성 사실만으로 합의·승인으로 보지 않습니다.
- 공통 계약(SPEC.md, `contracts/`, 공통 사전) 변경이 필요하면 AGENTS.md §3 절차를 따로 밟습니다.

- 참여자: 팀장 (팀원 확인 전)
- 근거: SPEC §1~§3, §12, docs/next-work-spec.md T1

### 결정

제안대로 채택합니다. SPEC.md v0.1을 **개발 준비 기간(10/16~18)의 작업 기준**으로 사용하고, 아래 보류 쟁점은 해당 작업(T2~T5)에서 결정한 뒤 SPEC을 갱신합니다.

- 목표·우선순위(§1), P0 범위·제외 범위(§2), 일정(§3), 처리 규칙(§6), 보안(§10), 완료 기준(§11)은 그대로 채택합니다.

### 영향

- 채택 시 SPEC.md 상태 문구("제안 초안")를 기준 버전으로 바꾸는 변경은 AGENTS.md §3 절차로 별도 PR에서 진행합니다. 이 결정은 SPEC을 수정하지 않습니다.

## D-002. 역할 분담

- 상태: **팀장 결정 (팀원 확인 전)** — 안 B로 시작
- 작성일: 2026-10-16 / 팀장 결정: 2026-10-17
- 참여자: 팀장 (팀원 확인 전)
- 근거: SPEC §8

팀장은 전체 의사결정·통합·병합을 맡습니다. 주 담당은 개발 소유권이며, 다른 사람의 검토·협업을 막지 않습니다.

### 안 A — SPEC §8 기본안

| 영역 | 주 담당 | 검토 | 경계 |
|---|---|---|---|
| SPEC·contracts·공통 사전 | 팀장 | 팀원 | 변경 전 영향 공유 (D-003) |
| 분석·검증·추천·Firebase·보안 | 팀장 | 팀원 | 공통 계약에 맞춰 결과 제공 |
| 수집 파이프라인(저장·중복·수정 감지·실패 기록)·배포 | **미정** | — | SPEC §8 기본표에 담당이 없음("저장은 공통 코드"만 명시). 질문 1에서 결정 |
| 수집 어댑터 1개 | 팀원 | 팀장 | RawNotice 출력까지. DB 저장은 하지 않음 |
| Flutter 피드·상세·저장 UI | 팀원 | 팀장 | 샘플 Repository로 선행 개발. 인증·실데이터 연동은 팀장 지원 |
| 통합·오류 검증·보고 | 팀장 주도 | 공동 수행 | 원문 대비 검증, 실기기 시연 |

### 안 B — 팀원 부담 조정안 (SPEC §8 단서)

수집 어댑터와 UI를 동시에 맡기 어려우면 팀장이 **수집 파이프라인과 배포**를 맡고, 팀원은 어댑터 1개와 화면에 집중합니다. 안 A와의 차이는 아래 한 줄입니다.

| 영역 | 안 A | 안 B |
|---|---|---|
| 수집 파이프라인·배포 | 미정 (팀원 또는 공동 가능) | 팀장 |

### 이유

- 팀장이 계약·분석·추천·보안을 함께 맡아 계약 변경과 소비 코드를 한 사람이 맞출 수 있습니다 (AGENTS.md §3 같은 PR 갱신 규칙).
- 어댑터 책임을 RawNotice 출력까지로 끊어 팀원 작업이 저장·분석 구조에 묶이지 않게 합니다.

### 결정 (2026-10-17, 팀장)

| 질문 | 결정 |
|---|---|
| 1. 안 A / 안 B, 재조정 시점 | **안 B**. 수집 파이프라인·배포는 팀장 담당. 정기 재조정 시점은 두지 않고 필요할 때 조정 |
| 2. 팀원의 Flutter 개발 환경·Android 기기 준비 | **미확인**. 실제 설치·실행 결과는 T3에서 기록 |
| 3. 출처 허가 대기 중 팀원 작업 | 승인된 계약과 샘플 Repository로 피드·상세·저장 **화면 선행 개발** |
| 4. Firebase 프로젝트 소유·콘솔 권한 | **팀장 계정 소유**, 팀원은 필요한 범위만 권한 부여. 프로젝트 생성은 팀장의 별도 요청 전까지 하지 않음 |

## D-003. 파일 소유권과 공동 파일 변경 절차

- 작성일: 2026-10-16 / 팀장 결정: 2026-10-17
- 참여자: 팀장 (팀원 확인 전)
- 근거: SPEC §8 권장 구조, AGENTS.md §2·§3

### 이유

- SPEC §8의 "같은 파일 동시 수정 회피, 작은 PR"을 경로 단위로 구체화합니다.
- main 보호 설정이 적용되지 않아(아래 현재 제약) 경계를 문서 규칙으로라도 명확히 해야 합니다.

### 파일 경계 (D-002 기준)

| 경로 | 주 담당 | 다른 사람이 수정할 때 |
|---|---|---|
| `apps/mobile/` | 팀원 | 인증·데이터 연동 부분은 팀장이 PR로 제안 |
| `backend/collectors/<출처>/` | 팀원 | 공통 인터페이스 변경은 팀장과 사전 협의 |
| `backend/collectors/` 공통 코드(파이프라인) | 팀장 (D-002 안 B) | 주 담당이 아닌 사람은 PR로 제안 |
| `backend/analysis/`, `backend/recommendation/`, `backend/api/` | 팀장 | 팀원은 PR로 제안 |
| `fixtures/` | 해당 계약 작성자 | 계약 변경과 같은 PR에서 갱신 |

폴더는 실제 작업이 시작될 때 만듭니다. 이 표는 생성 지시가 아닙니다.

### 공동 파일

`SPEC.md`, `contracts/`, 공통 사전, `AGENTS.md`, `README.md`, `docs/decisions.md`, `.env.example`, `.gitignore`, `.github/`

- 변경 전에 이유와 영향을 PR 또는 이슈에 적고 팀장 승인 후 진행합니다 (AGENTS.md §3).
- 단, `docs/decisions.md`의 본인 확인란 기입은 각자 PR에서 할 수 있습니다. 결정 내용 자체의 수정은 위 절차를 따릅니다.
- `docs/handoff.md`는 각자 PR에서 갱신할 수 있습니다. 충돌을 줄이기 위해 자기 작업 줄만 고치고, 병합 시 팀장이 정리합니다.
- 같은 파일을 동시에 수정해야 하면 먼저 알리고 한쪽 PR이 병합된 뒤 이어서 작업합니다.

### 현재 제약

- main 보호 설정은 GitHub 요금제 제한(HTTP 403)으로 적용되지 않았습니다. 위 경계와 PR 경유는 기술적으로 강제되지 않으며 규칙으로 운영합니다.
