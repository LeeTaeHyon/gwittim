## 0. 먼저 볼 결론

1. 소개문서의 분류 수치는 원자료에서 그대로 재현된다. 다만 47건으로는 "자체 모델이 Gemma보다 낫다"를 말할 수 없다(§1.2).
2. 시험 세트 47건은 무작위 표본이 아니고, 정답을 Gemma 답이 보이는 표에서 매겼다(§1.3). 2주차 전후 비교 전에 잣대를 다시 세워야 한다.
3. 4주 동안 새로 오는 알림톡은 약 15건이다. 2주차의 재료는 새 자료가 아니라 **이미 있는 287건에 사람 정답을 붙이는 것**이다(§1.4, §3.2).
4. 1주차·3주차는 SPEC의 P0 제외 항목과 정면으로 겹친다(§5). 구현 전에 범위 결정이 필요하다.
5. 앱의 핵심 주장인 지원 조건 판정은 아직 정답 대조 평가가 없다. 저장된 '제한 없음' 5건 중 4건이 미해석 조건이 있거나 추출이 불완전하다(§1.5).

### 1.3 시험 세트의 문제 [실행·읽음]

- **무작위 표본이 아님** [실행]: `make_review_set.py`가 규칙과 Gemma의 관심사 판단이 갈린 공지를 절반 뽑는다. 갈린 공지는 전체의 23%(67/287)인데 시험 세트에서는 53%(25/47)다. 전체 비율로 다시 가중하면 종류 정확도는 규칙 38%, Gemma 52%, 자체 54%다(층이 작아 참고치).
- **정답이 Gemma 답에 끌렸을 수 있음** [읽음]: `review_set.csv`는 규칙·Gemma의 답과 Gemma 근거를 정답 칸 옆에 보여 준다.
- **검수자 수와 독립 여부 기록 없음** [미확인].
- **자체 모델이 맞힐 수 없는 정답** [실행]: 종류 정답 47건 중 7건이 `other`인데 자체 모델의 출력 12개에 `other`가 없다. 지금 모델의 상한은 40/47이다.
- **배운 꼬리표가 3개인 이유** [실행]: Gemma 라벨 기준 `culture_arts`는 287건 중 15건인데 학습 세트에서 5건 미만이라 빠졌다. 시험 정답에는 7건 있다.

### 1.4 필요한 시험 세트 크기 [실행]

| 목표 | 필요한 건수 |
|---|---|
| 정확도 95% 구간 반폭 ±10%p | 89 |
| 반폭 ±7%p | 181 |
| 반폭 ±5%p | 355 |
| 두 방법의 정확도 차 15%p 검출(양측 5%, 검정력 80%) | 57~103 |
| 차 10%p 검출 | 132~233 |
| 차 5%p 검출 | 532~939 |

- 범위는 두 방법이 서로 다르게 맞히는 비율을 17%(관측값)~30%로 둔 것이다.
- 알림톡은 주 3.6건꼴로 온다(데이터루프 설계 초안, 정규식 추정 [읽음]). 4주에 약 15건이라 새 자료로는 어떤 차이도 검출할 수 없다.

**추천안: 287건 전부에 사람 정답을 붙이고 교차 검증으로 평가한다.**

- 라벨: 2명이 따로, 원문만 보고(규칙·Gemma 답을 가린 표) 관심사·종류·전체 대상을 매긴다. 기존 47건도 다시 매긴다.
- 일치도: Cohen κ를 종류와 관심사 꼬리표별로 계산한다. 갈린 건은 둘이 합의해 정하고 합의 전 답을 남긴다.
- 평가: 방(6개)과 종류로 층을 나눈 5겹 교차 검증을 씨앗 5개로 반복한다. 접힌 예측을 모아 McNemar와 부트스트랩 구간을 낸다. 287건이면 반폭 약 ±6%p, 10%p 차를 검출할 수 있다.
- 동결: 라벨 파일의 SHA-256과 겹 나눔 씨앗을 `docs/decisions.md`에 적은 뒤에 학습을 시작한다. 원문은 저장소에 넣지 않는다.
- 품: 240건 × 2명, 건당 수십 초. 한 사람에 2~3시간.
- 학습 정답은 지금처럼 Gemma 라벨을 쓸 수 있다. 사람 정답은 채점과, 2주차의 '오류 사례' 판정에 쓴다.

### 1.5 게시판 조건 추출 평가 설계

| 항목 | 건수 |
|---|---|

- 원자료: `data/local/pipeline/records.json`에 본문 글자와 첨부 목록이 있다. 원문 HTML과 포스터 이미지는 저장돼 있지 않다 [실행]. 정답을 매길 때는 `source_url`로 원문 페이지와 포스터를 직접 본다.

평가 설계:

- 표본: 게시판 164건에서 게시판별 비례로 100건(공지 34, 채용 34, 장학 20, 근로 12). 씨앗 고정.
- 정답: 2명이 원문만 보고 마감일, 학교·학과·학년·재학 조건, 자유 문장 조건(성적·소득·어학 등) 목록, '누구나 지원 가능' 여부를 적는다. 분석 결과는 가린다.
- 지표
  - 마감일: 날짜 완전 일치 정밀도·재현율. 틀린 날짜 건수.
  - 구조 조건(학과·학년·재학): 조건 단위 정밀도·재현율.
  - 자유 문장 조건: 정답 조건이 `conditions` 또는 `unresolved_conditions`에 잡힌 비율(놓친 조건 수).
  - 판정: 프로필 4개(소개문서의 두 프로필 + 졸업생 + 1학년)로 `evaluate`를 돌려 정답 판정과의 혼동표.
- **1순위 지표: 틀린 '지원 가능'.** 정답이 `not_met` 또는 `needs_check`인데 `met`으로 나온 건수. 합격 기준 0건.
- 수정 명세의 W1을 적용하기 전과 후를 같은 100건으로 잰다.

## 2. 주차별 전제 깨기 실험

각 주차에서 가장 먼저 틀릴 수 있는 전제 하나와, 하루 안에 확인하는 방법.

### 2.1 1주차 — 폰 안에서 알림톡 분류

**전제 A: 폰 알림에 알림톡 본문이 분류할 만큼 들어 있다.** [미확인: 2026-11-10 `adb devices`에 연결된 기기 없음]

- 방법: 학교 채널 알림톡이 온 직후 S25 Ultra에서 `adb shell dumpsys notification --noredact`. 카카오톡 알림의 제목·본문·확장 본문 칸에 든 글자 수, 방 이름이 어디에 오는지, 이미지형·버튼형 알림톡이 어떻게 보이는지를 6개 방에서 각 1건 이상 적는다.
- 덤프에는 다른 알림도 들어 있다. 카카오톡 학교 채널 부분만 남기고 저장소에 넣지 않는다.
- 미리 잰 값 [실행]: 내보내기 본문의 앞부분만 넣었을 때 전체 본문 판정과 같은 비율(287건)

| 들어오는 길이 | 관심사 판정 일치 | 종류 일치 | 애매 비율 |
|---|---|---|---|
| 앞 40자 | 215 (75%) | 224 (78%) | 47% |
| 앞 100자 | 255 (89%) | 251 (87%) | 25% |
| 앞 200자 | 273 (95%) | 269 (94%) | 22% |
| 앞 300자 | 277 (97%) | 268 (93%) | 23% |
| 본문 전체, 제목 줄 없음 | 279 (97%) | 277 (97%) | — |

- 본문 중앙값은 354자, 10%는 214자 이하다. 알림에 200자 미만만 온다면 1주차는 "알림을 눌러 연 뒤 화면에서 읽기"나 "복사해 붙여넣기"로 설계를 바꿔야 한다.
- 합격 기준: 실제 알림 본문으로 분류한 결과가 같은 공지의 내보내기 본문 판정과 95% 이상 일치.

**전제 B: Dart로 옮긴 계산이 서버와 같은 판정을 낸다.** [읽음]

- 글자 단위 모델이라 글자를 나누는 방식이 같아야 한다. 파이썬은 코드 포인트로 나누는데 Dart 문자열은 UTF-16 단위다. `runes`로 나눠야 한다. 이모지처럼 두 단위로 표현되는 글자가 있는 공지가 287건 중 81건이다 [실행].
- ASCII만 소문자로 바꾸기, 문장부호 정규식, 600자 자르기, 링크 지우기를 `text_model.py`와 똑같이 옮긴다.
- 검증: 합성 문장 골든 파일(지금 3개 → 50개 안팎. 이모지, 전각 문자, 로마 숫자, 600자 초과, 빈 글, 링크만 있는 글 포함)을 저장소에 두고 Python·Dart 테스트가 같은 파일을 읽는다. 287건 비교는 로컬 스크립트로 돌린다.
- 합격 기준: 골든 전부 확률 차 1e-5 이하, 287건 판정 287/287.

**전제 C: 개인 알림을 기기에서 먼저 거른다.** [읽음]

- 학교 채널에는 수강 미제출 같은 개인 알림도 온다. 지금은 `backend/collectors/mjc_kakao/parser.py`의 `classify`·`mask`가 거르고 가린다. 이 규칙도 Dart로 옮겨야 하고, 같은 방식의 골든 검증이 필요하다.
- "서버로 보내지 않음"이면 분류 결과는 그 폰에서만 쓴다. 결과를 어디에 보여 줄지는 §6 질문 1.

지연 시간: 프로파일 빌드, 287건 반복, p50·p95. S25 Ultra 한 대뿐이라 낮은 사양 값은 에뮬레이터 참고치로만 적는다. 합격 기준 p95 50ms 이하(서버 CPU 35ms 기준).

### 2.2 2주차 — 오류 사례 재학습

**전제: 4주 안에 차이를 잴 만큼 오류 사례가 모인다.** 새 자료로는 성립하지 않는다(§1.4).

- 새 알림톡 약 15건 중 애매 판정은 21%꼴, 3건 안팎이다. 사용자가 고친 사례는 고치는 화면도 동의 절차도 아직 없다 [읽음].
- 그래서 오류 사례는 기존 287건에서 만든다: 사람 정답과 모델 답이 다른 공지 + 캐스케이드가 애매하다고 본 61건.
- 치우침 대책: 오류 사례만으로 학습하지 않는다. 기존 학습 자료에 섞고, 겹 나눔은 §1.4의 동결본을 쓴다. 꼬리표별 재현율을 전후로 비교해 3개 꼬리표(ai_data, global_language, media_content) 중 떨어진 것이 없는지 본다.
- '새로 배운 관심 분야 수': 학습 예시 5건 이상이 기준이다. Gemma 라벨 기준 culture_arts 15, design 8, health 6, education_welfare 5건이라 겹 나눔만 바꿔도 늘어날 수 있다 [실행]. 사람 정답 기준 건수는 라벨을 붙인 뒤 다시 센다.
- 문턱 재조정: 꼬리표 문턱 0.2와 기타 문턱 0.15는 검증 35건으로 정했다. 교차 검증의 접힌 예측으로 보정 곡선(ECE)과 "Gemma 호출률 대 F1" 곡선을 그려 다시 정한다.
- 종류 모델에 `other`를 넣을지도 이때 정한다(§1.3).

### 2.3 3주차 — 교외 공고 에이전트

**전제 A: 찾을 출처의 수집·저장·재표시가 허용된다.** [미확인: 후보 출처를 아직 정하지 않았다]

- 방법: 후보 출처 3~5곳을 팀장이 정하면 [source-review.md](source-review.md) §2와 같은 표(robots.txt, 이용약관, 저작권 표시, 로그인 필요 여부, 범위별 상태)를 출처마다 만든다.
- 허용이 확인된 출처만 허용 목록에 넣는다. 에이전트는 허용 목록 밖 주소를 열지 않는다.

**전제 B: 검색 수단의 비용이 하루 한도 안이다.** [미확인: 수단 미정, 유료면 승인 필요]

| 후보 | 비용 | 한계 |
|---|---|---|
| 허용 목록 사이트의 목록 페이지를 직접 조회 + 로컬 Gemma로 판별 | 0원 | 검색이 아니라 정해진 곳 탐색. 지금 수집기와 구조가 같음 |
| 검색 API + 로컬 Gemma | 요금표 확인 필요 | 결과 주소가 허용 목록 밖일 수 있음 |
| 외부 LLM의 웹 검색 도구 | 요금표 확인 필요 | 공고 본문이 외부로 나감. D-004(로컬 우선)와 충돌 |

- 고르지 않는다. 팀장이 출처 범위와 비용 상한을 정한 뒤 정한다.

**전제 C: "근거가 확인된 비율"만으로는 옳다고 할 수 없다.**

- 그 지표는 찾은 것만 본다. 놓친 공고와 중복은 따로 잰다.
- 기준 목록: 평가 주간 하루를 정해 허용 출처에서 사람이 조건에 맞는 공고를 전부 적는다(출처당 30분 안팎). 에이전트가 그중 몇 건을 찾았는지가 재현율이다.
- 재생 평가: 에이전트가 받은 응답(상태 코드, 최종 주소, 시각, 본문 해시, 본문)을 로컬에 저장하고, 같은 응답으로 다시 돌려 같은 결과가 나오는지 본다.
- 웹 페이지 속 지시문: 받은 본문은 자료로만 넣고 도구 호출 권한과 분리한다. "이전 지시를 무시하라" 같은 문장을 심은 합성 페이지 5개로 허용 목록 밖 접근이 0건인지 본다.

### 2.4 4주차 — 사용자 테스트

**전제: "추천이 맞다고 본 비율"은 자기 보고라 옳고 그름을 가리지 못한다.**

- 정답이 미리 정해진 과제로 바꾼다. 팀 휴대폰에 프로필을 정해 두고, 그 프로필의 정답은 §1.5의 정답표에서 가져온다.

| 과제 | 정답 판정 |
|---|---|
| 이 프로필로 지금 지원할 수 있는 공고 3개 고르기 | 정답표의 판정과 일치 |
| 정해 준 공고에 지원할 수 있는지, 왜인지 말하기 | 판정과 조건 문구 일치 |
| 정해 준 공고의 마감일 말하기 | 날짜 일치 |
| '확인 필요' 공고에서 무엇을 확인해야 하는지 찾기 | 미해석 조건 문구 중 하나 |
| 이번 주 마감 공고를 달력에서 찾아 저장하기 | 저장 목록에 그 공고 |

- 기록: 화면 녹화와 말한 내용 그대로(소리 내어 생각하기). 과제별 성공·시간·막힌 곳. 설문은 SUS 10문항만 덧붙인다.
- 5명 결과는 비율이 아니라 건수로 적는다("5명 중 4명"). 틀린 '지원 가능'을 믿고 지원 가능하다고 답한 경우는 따로 센다.
- 녹화·녹음은 참가 동의가 필요하다(§5).

## 6. 팀장이 정할 것

1. **1주차 범위**: P0 제외인 '알림톡 자동 수신'을 2단계 범위로 넣을지. 넣는다면 폰에서 분류한 결과를 그 폰에서만 보여 줄지.
2. **라벨 작업자**: 알림톡 287건과 게시판 100건을 2명이 따로 매긴다. 팀원이 두 번째 작업자를 맡을 수 있는지.
3. **3주차 출처와 비용**: 후보 출처 3~5곳, 하루 비용 상한(0원이면 표의 첫째 안만 가능), 외부 LLM 허용 여부.
4. **4주차 참가자**: 재학생 5명 모집 방법, 녹화·녹음 동의를 받을지.
5. **처리방침 개정 시점**: 1주차 기능을 체험판 빌드에 넣기 전에 개정본을 먼저 공개할지.

## 7. 실행한 검증과 한계

- [실행] 분류 수치 재현, Wilson·McNemar·부트스트랩, 표본 크기 계산, 시험 세트 구성 비교, 잘린 본문 모의 실험, 꼬리표 건수, 게시판 저장 공고 집계. 저장소 코드와 `localModel`·`data/local` 원자료를 읽기만 했고, 저장소 파일은 이 문서만 새로 만들었다. 계산 스크립트는 저장소에 넣지 않았다.
- [실행] Keras 대 표준 라이브러리 287건 비교는 `localModel/.venv`(TensorFlow)로 따로 돌렸다. `export_weights.py`는 모델 파일을 다시 쓰므로 쓰지 않았다.
- [미실행] 폰 알림 덤프: 연결된 기기 없음.
- [미실행] 교외 출처 조사, 검색 수단 요금 확인: 출처·수단 미정.
- [미실행] `uv run pytest`, `flutter test`: 코드를 바꾸지 않았다.
- 한계
  - 잘린 본문 실험은 "전체 본문 판정과 같은가"만 본다. 정답과 맞는지는 사람 정답이 붙은 뒤에 잰다.
  - 다시 가중한 정확도(§1.3)는 층이 22·25건이라 참고치다.
  - 알림톡 주 3.6건은 설계 초안의 정규식 추정값을 읽은 것이다.
  - 부트스트랩은 씨앗 0, 5,000회다.
