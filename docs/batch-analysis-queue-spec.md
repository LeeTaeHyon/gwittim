# 교외 수집과 Gemma 분석 대기열 분리 명세 (하위 에이전트용)

- 작성: 2026-11-28, 팀장 결정
- 기준: `origin/main` `1563010`. worktree `.claude/worktrees/batch-analysis-queue`, 브랜치 `feat/batch-analysis-queue`
- 커밋·PR·배포·Firestore 쓰기 금지. `Gwittim-batch` 폴더·예약 작업 수정 금지. 운영 데이터 폴더(`Gwittim/data/local`)에 쓰지 않음(사본으로 시험)

## 1. 배경

- 지금 교외 출처는 출처마다 '수집 → Gemma 분석 → 게시'를 한 번에 하고, 교외 단계 30분 상한(`scripts/run_batch.ps1` `$externalBudgetSeconds`)이 분석 시간까지 포함한다
- 11/27 09:00 배치: 링커리어·위비티에서 시간을 다 써 콘테스트코리아·씽굿·올콘을 통째로 건너뜀. 18:00 배치: 올콘이 남은 96초로 시작해 도중 멈춤
- 분석을 끄면 안 된다: 규칙 분석만 쓰면 `summary`가 null이고(`backend/analysis/rules.py`), Gemma는 마감·지원 조건 해석도 맡는다
- 로컬 처리량이 부족하다는 근거는 없다(11/27 이틀 새 출처 분석 약 280건). 문제는 수집과 분석이 같은 상한 안에 줄 선 것

## 2. 팀장 결정 (2026-11-28)

- 수집 단계와 Gemma 분석 대기열을 나눈다
- 기존 공고는 재분석하지 않는다. 분석 버전(`ANALYSIS_VERSION`, 모델 버전)을 바꾸지 않는다
- 게시 규칙은 그대로: 검증 통과면 게시, 아니면 review_pending, 이미 끝난 공고는 처음부터 게시 안 함, D-048 출처 우선순위 중복 처리

## 3. 범위

- 교외 출처 7개(`linkareer_activity`, `linkareer_contest`, `wevity`, `wevity_activity`, `contestkorea`, `thinkgood_contest`, `allcon_contest`)만
- 명지 게시판·숭의·알림톡 단계는 그대로
- 백필(`--backfill`) 동작은 그대로 둔다(같은 코드 경로를 쓰게 되면 결과가 지금과 같은지 테스트로 확인)

## 4. 구조

### 4.1 수집 단계 (출처별, 분석 없음)

- `backend/collectors/common/external_cli.py`에 수집 전용 실행(예: `--collect-only`)
  - `source.collect` → `ingest`(파이프라인 저장, new/changed/unchanged 판정) → 분석 대기열에 넣고 끝
  - 대기열에 넣는 것: 이번에 new 또는 changed인 공고만. unchanged는 넣지 않음
  - 수집 상한(목록 5쪽·상세 50건·요청·robots·3초 간격·멈춤 규칙)은 지금과 같다
- 수집에 쓰는 시간 상한은 따로: 교외 수집 전체 20분(값과 근거는 실측으로 조정해 보고)

### 4.2 분석 대기열

- 파일: `data/local/analysis_queue.json` (출처·키·넣은 시각·사유 new/changed). 배치 사이에 남는다
- 같은 키가 다시 들어오면 한 건으로 합치고 넣은 시각은 처음 값 유지
- 처리 순서: D-048 출처 우선순위(위비티 공모전 > 위비티 대외활동 > 콘테스트코리아 > 링커리어 공모전 > 링커리어 대외활동 > 씽굿 > 올콘) 안에서 오래 기다린 순
  - 이유: 우선 출처가 먼저 분석돼야 뒤 출처의 같은 공고가 처음부터 중복으로 묶인다. 순서를 바꿔도 최종 게시 결과가 지금(출처를 순서대로 돌린 결과)과 같은지 테스트로 확인

### 4.3 분석 단계 (한 번, 모든 출처)

- 새 실행 진입점(예: `python -m backend.collectors.common.analyze_queue --data-dir ... --max-seconds ...`)
  - 대기열에서 꺼내 기존 `_external_notice`(→ `build_notice` → 검증 → `_publish`) 그대로 처리
  - 시간 상한(예: 30분)에 닿으면 남은 건은 대기열에 두고 끝
  - 실패(Ollama 응답 없음 등)는 지금처럼 규칙 분석으로 폴백하되, 폴백 결과는 지금과 같은 방식으로 기록(버전 접미사 등 기존 동작 유지)
  - Gemma 언로드는 분석 단계 끝에 한 번
- 이번에 목록에 안 보인 기존 공고의 날짜 재판정(마감 지나면 closed)은 지금처럼 네트워크 없이 하되, 분석 버전이 같아 `build_notice`가 이전 분석을 재사용하는지 확인(LLM 호출 0)

### 4.4 배치 스크립트

- `scripts/run_batch.ps1` 교외 부분: ① 7개 출처 수집(수집 상한) → ② 분석 단계 1회(분석 상한) → 알림톡 단계
- 전체 배치가 1시간 안에 끝나게 상한을 정하고 근거를 주석에 남긴다
- 완료 알림(토스트)·요약에 교외 게시 수와 대기열 수를 함께

## 5. 기록 (매 배치 로그 한 줄 JSON)

- 수집: 출처별 새·바뀜·변화 없음·대기열에 넣은 수, 멈춤 사유
- 분석: 처리 수, LLM 분석 수, 폴백 수, 게시·검토 대기·중복·끝난 공고 수, **남은 대기 건수, 가장 오래 기다린 공고의 대기 시간(분)**, 출처별 남은 수
- 이 두 값이 여러 회차 연속으로 늘면 API 시범 적용을 검토한다(이번 범위 아님)

- 명지·숭의·알림톡 수집기
- 배치 로그 한글 깨짐(별건)
- `Gwittim-batch` 폴더, 예약 작업, Firestore

## 7. 검증

- `uv run pytest` 전체, `tools/validate_contracts.py`
- 새 테스트(메모리 저장소·가짜 분석기)
  - 수집만 하면 분석기 호출 0, 대기열에 new·changed만 들어감
  - 같은 입력을 '지금 방식'과 '수집→대기열→분석' 방식으로 돌렸을 때 게시·review_pending·중복·끝난 공고 결과가 같음(출처 여러 개, 같은 공고가 두 출처에 있는 경우 포함)
  - 분석 상한에 닿으면 남은 건이 다음 실행에 이어서 처리되고, 이미 처리한 건은 다시 분석되지 않음
  - 기존 공고(같은 분석 버전)는 LLM 호출 없이 재사용
  - 대기열 파일이 깨졌거나 없을 때 안전하게 시작
- 실데이터 시험(로컬 사본, Firestore 변수 비운 상태)
  - `Gwittim/data/local`의 `pipeline/`·`notices.json`·`external_*.json`을 임시 폴더로 복사해 `--data-dir`로 지정
  - 출처 2곳(예: 링커리어 대외활동, 올콘)을 `--pages 1 --max-items 5`로 수집만 → 분석 단계 1회(Gemma 로컬). D-038 접근 규칙 지킴, 시험 수집은 출처당 1회
  - 결과 JSON 두 줄과 대기열 수 변화를 보고
