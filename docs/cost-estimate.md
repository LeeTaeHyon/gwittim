## 2. 사용량 가정 (D-006 운영값 기준)

| 항목 | 가정 |
|---|---|
| 수집 배치 | 3시간마다(하루 8회) 공지사항 2페이지. 새 글·수정 글만 Firestore에 씀 (같은 버전은 쓰지 않음, W4) |
| 공개 공고 수 | 초기 약 40건 → 학기 동안 수백 건 |
| 사용자 | 중간보고까지 50명, 공개 테스트 200명 |
| 사용 패턴 | 1인당 하루 피드 10회, 상세 5회, 저장·프로필 2회 |
| 서버 | Cloud Run 최소 인스턴스 0 (요청 없을 때 과금 없음), 요청당 약 0.1초·1 vCPU·512 MiB |

## 3. 추정

| 항목 | 50명 | 200명 | 무료 한도 대비 |
|---|---|---|---|
| Firestore 쓰기 (배치 + 프로필·저장) | 약 200/일 | 약 1천/일 | 2만/일의 5% 이하 |
| Firestore 읽기 — 캐시 없음 (요청마다 공고 300건 전체) | 약 15만/일 | 약 60만/일 | **한도 초과 3~12배** |
| Firestore 읽기 — 5분 캐시 (이번 변경) | 약 1~3천/일 | 약 3~6천/일 | 한도의 10% 이하 |
| Cloud Run 요청 | 약 2.5만/월 | 약 10만/월 | 200만/월의 5% 이하 |
| Cloud Run CPU | 약 2.5천 vCPU-초/월 | 약 1만 | 18만의 6% 이하 |
| Authentication | 50 MAU | 200 MAU | 5만의 1% 이하 |
| Artifact Registry | 이미지 약 0.47 GB × 보관 개수 | 같음 | 이미지 2개 보관 시 약 0.4 GB 초과 → 월 약 $0.04 |

- **캐시를 추가했습니다.** 캐시가 없으면 추천 요청마다 공개 공고 전체를 읽어 Firestore 무료 읽기를 넘습니다. 그래서 `CachedNoticeReader`(5분)를 서버에 적용했습니다. 공고는 3시간마다만 바뀌므로 5분 지연은 문제가 없습니다.
- 캐시가 없어 초과하더라도 금액은 작은 편입니다(일 수십만 건 읽기는 월 수 달러 수준으로 추정). 다만 단가를 확인하지 못했으므로 캐시를 기본으로 둡니다.
- **결론:** 50~200명 규모는 무료 한도 안입니다. 비용이 생길 수 있는 항목은 Artifact Registry 이미지 보관(월 몇십 원 수준)뿐이며, 보관 이미지를 1~2개로 정리하면 0에 가깝습니다.

## 4. 비용 사고 방지 (Firebase 프로젝트를 만들 때 함께)

1. 결제 계정에 **예산 알림**을 설정합니다(예: 월 $1, $5, 50%·90%·100% 알림). 알림은 지출을 막지 않으므로 보고 대응해야 합니다.
2. Cloud Run은 **최소 인스턴스 0**, **최대 인스턴스 2~3**으로 제한합니다. 트래픽 폭주나 공격 시 비용 상한 역할을 합니다.
3. Artifact Registry에 **정리 정책**(최근 이미지 2개만 보관)을 겁니다.
4. Firestore 보안 규칙(W4)으로 클라이언트의 공고 쓰기·대량 읽기 경로를 막습니다(로그인 사용자만 읽기).
5. dev 프로젝트는 테스트 후 사용하지 않으면 정리합니다.
