## 2. 단계 1: 지원 건 상태

**모델**

```dart
enum CaseState { saved, preparing, applied, skipped, missed, closed, removed }

class ApplicationCase {
  final String noticeId;
  final CaseState state;
  final CaseState? previous;      // 되돌리기·되살리기용 바로 전 상태(saved·preparing·applied·skipped 중)
  final DateTime changedAt;       // 기기 시각
  final String? seenDeadline;     // 리포트를 연 때의 마감 'YYYY-MM-DD HH:MM'(시각 없으면 날짜만). 마감 변경 표시 한 번만 보이기용
  final String? emphasizedOn;     // 마지막으로 강조(말풍선 건수·브리핑 카드)에 들어간 날 'YYYY-MM-DD'
  final String? eligibilityStatus; // 서버 판정 met / needs_check / not_met. 모르면 null(팀장 결정 2026-11-24)
  final DateTime? eligibilityAt;   // 그 판정을 받은 시각(기기 시각)
  final DateInfo? applicationStart; // 공고 상세에서 복사(목록 요약에는 없음, 팀장 결정 2026-11-24)
  final String? applyUrl;           // 공고 상세에서 복사
  final int? detailVersion;         // 위 두 값을 받은 notice_version. null이면 아직 못 받음
}
```

**전이**(care-loop-spec §4.3과 같음)

| 출발 | 사건 | 도착 | 주체 |
|---|---|---|---|
| 없음 | 저장 | saved | 사용자 |
| saved | '준비 시작' | preparing | 사용자 |
| saved·preparing | '신청함' | applied | 사용자 |
| saved·preparing | '이번엔 안 함' | skipped | 사용자 |
| applied·skipped | '되돌리기' | previous | 사용자 |
| saved·preparing | 마감이 지남(§3.3) | missed | 날짜 |
| missed | 마감이 뒤로 바뀌어 아직 안 지남 | previous | 공고 변경 |
| saved·preparing·missed | lifecycle closed | closed | 공고 변경 |
| closed | lifecycle open | previous | 공고 변경 |
| 모든 상태 | lifecycle removed | removed | 공고 변경 |
| 모든 상태 | 공고가 저장 목록 응답에 없음(다른 기기에서 저장 취소, 공고 문서가 사라짐) | 기록 지움(이번 실행에 이 기기로 저장한 공고는 빼고) | 공고 변경 |
| 모든 상태 | 저장 취소·'목록에서 지우기' | 기록 지움 | 사용자 |

- 날짜·공고 변경 전이는 저장하지 않고 **읽을 때 계산**한다(`effectiveState(case, notice, now)`). 기기에 남기는 것은 사용자 전이와 `previous`·`seenDeadline`·`emphasizedOn`뿐. 그래야 마감이 늦춰지면 저절로 되살아남
- 마감이 null이면 missed가 되지 않음

**판정 저장(팀장 결정 2026-11-24)**
- 저장할 때 그 화면에 추천 정보(`Recommendation`)가 있으면 그 `eligibilityStatus`와 받은 시각을, 없으면 null로 기록
- 추천 목록(`listRecommendations`)을 받을 때마다 저장소 한 곳에서, 목록에 있는 지원 건의 판정 값과 시각을 갱신(화면마다 따로 고치지 않음)
- 학교·학과·학년·재학 상태가 바뀌면 모든 지원 건의 판정 값을 null로 지우고, 그 뒤 받는 새 추천 목록으로 다시 채움(AI 전송 동의·관심 분야만 바뀐 저장은 그대로)
- 추천 목록에 없는 공고는 값이 그대로(처음부터 없었으면 null)

**신청 시작·신청 사이트 복사(팀장 결정 2026-11-24)**
- 목록 요약(`notice_summary`)에는 두 값이 없어, 지원 건에 상세 값을 복사해 두고 모든 화면은 지원 건의 값만 읽음. 계약은 건드리지 않음
- 받는 때: 저장 직후(뒤에서, 화면을 막지 않음), 리포트가 상세를 받았을 때, 저장 목록·추천 목록의 요약 notice_version이 기록된 버전과 다를 때(기록이 없는 건 포함)
- 실패하면 버전을 적지 않고 두어 다음 목록 갱신 때 다시 시도. 못 받은 동안은 신청 시작 항목이 없고 신청 경로는 원문으로

**저장**
- shared_preferences 키 `application_cases`: `{noticeId: {...}}` JSON 하나. 읽기·쓰기 실패는 앱을 멈추지 않고 빈 상태로(기존 `major_picks`와 같은 방식)
- 앱 전체가 나눠 쓰는 저장소 하나(`ChangeNotifier` 등)를 `main.dart`에서 만들어 탭·리포트에 넘김. 한 곳에서 바꾸면 홈·저장함·달력이 다시 받지 않아도 바로 바뀜
- 저장(`saveNotice`)이 성공하면 saved 기록을 만들고, 저장 취소(`deleteSaved`)가 성공하면 기록을 지움. 리포트·저장함 어디서 하든 같은 함수로
- 앱을 열 때 저장 목록에 없는 공고의 기록은 지움(다른 기기에서 저장 취소한 경우)
- 저장 목록에 있는데 기록이 없는 공고(이 기능 전에 저장, 다른 기기에서 저장)는 '저장' 상태로 기록을 만든다(결정 7 저장 = 지원 건 시작). 판정은 마지막 추천 목록에 있으면 그 값, 없으면 null(팀장 승인 2026-11-24)
- 기기 기록 읽기를 기다리지 않는다(기기 저장소가 응답하지 않아도 목록·저장이 멈추지 않게). 읽기가 늦게 끝나면 이렇게 합친다(팀장 승인 2026-11-24)
  1. 이번 실행에 사용자가 바꾼 기록(저장·상태 변경·되돌리기)은 지금 값
  2. 이번 실행에 저장 취소한 기록은 지운 채
  3. 목록에서 자동으로 만든 기록·판정 갱신은 기기에 있던 값
  4. 이번 실행에 모두 지웠으면(로그아웃·탈퇴) 기기 기록을 되살리지 않음
- 기기 쓰기는 기기 기록을 다 읽은 뒤, 그때의 최신 상태로 한다(읽기 전에 쓰면 기기 기록을 덮음)
- 탈퇴(`main.dart` `_deleteAccount`) 때 지움. 로그아웃 때도 지움(같은 기기의 다른 계정이 보지 않게). 로그아웃 경로가 없거나 애매하면 '정하지 못한 것'으로

**테스트**: 전이 표 전부, 되돌리기, 마감 연장으로 되살아남, 저장 취소 때 지움, 저장소 읽기 실패 때 빈 상태, 판정 저장(저장 시 rec 유무, 추천 목록으로 갱신, 프로필 변경 때 null로 지우고 다시 채움)

## 3. 단계 2: 문구 함수

`CaseView caseView(NoticeSummary n, ApplicationCase? c, {required DateTime now})` 하나만 만들고(신청 시작·신청 사이트는 지원 건에 복사한 값), 모든 화면은 이 결과 문자열을 그대로 쓴다. 화면에서 남은 날·상태 문구를 따로 만들지 않는다. 추천 정보(`Recommendation`)는 넘기지 않고, 판정은 지원 건에 저장된 값만 본다(§2 판정 저장).

```dart
class CaseView {
  final String? stateLabel;    // '저장' '준비 중' '신청함' '이번엔 안 함' '마감 지남' '모집 끝남' '학교 공지에서 삭제됨'. 지원 건이 아니면 null
  final CaseItem? next;        // 다음 할 일 하나. 끝난 상태면 null
  final List<CaseItem> items;  // 리포트 카드에 보일 전체 순서
  final String remaining;      // 남은 날 문구
  final bool ended;            // applied·skipped·missed·closed·removed
}
class CaseItem { final String text; final String kind; /* 확인·행동 */ final String? evidence; final String? url; }
```

### 3.1 할 일 항목(공고 필드만)

| 항목 | 조건 | 문구 | 근거(evidence) | url |
|---|---|---|---|---|
| 신청 시작 | 지원 건의 `applicationStart`가 지금보다 뒤 | 'M월 D일 HH:MM 신청 시작'(시각 없으면 'M월 D일 신청 시작') | `applicationStart.evidence` | — |
| 조건 확인 | 지원 건의 `eligibilityStatus == 'needs_check'` | '지원 조건 직접 확인' | 서버 판정(지원 건에 저장된 값) | — |
| 신청 경로 | 항상 | 지원 건의 `applyUrl` 있으면 '신청 사이트에서 신청', 없고 `sourceUrl` 있으면 '원문에서 신청 방법 확인', 둘 다 없으면 '받은 알림톡에서 신청 방법 확인' | null | `applyUrl` → `sourceUrl` → null |
| 마감 | 확정 마감 있음 | 'M월 D일 HH:MM 마감' 또는 'M월 D일 마감' | `applicationDeadline.evidence` | — |

- `deadlineNote`는 할 일로 쓰지 않음
- 지원 건의 판정 값이 null이면 조건 확인 항목을 만들지 않음(미상을 '확인 필요'로 바꾸지 않음). met·not_met도 이 항목을 만들지 않음
- 화면은 어디서 열었든(저장함·홈·달력·리포트) 같은 지원 건 값을 쓰므로 항목이 같음

### 3.2 다음 할 일 순서

1. 끝난 상태 → 없음
2. 신청 시작 전 → 신청 시작
3. saved이고 조건 확인 필요 → 조건 확인
4. 신청 경로
5. preparing이고 조건 확인 필요 → 조건 확인(숨기지 않고 신청 경로 다음)
6. 마감(맨 뒤, '다음 할 일'로는 고르지 않고 목록에만)

`next`는 1~5 중 첫 항목. `items`는 1~6 순서 전체.

### 3.3 남은 날 문구

- '지금 마감이 지났나'
  - 시각과 시간대가 모두 있으면(`precision == 'minute'`, `timezone != null`) 그 시각(Asia/Seoul을 기기 시각으로 바꿔 비교. 기기 시간대가 한국이 아닐 때의 처리는 지금 화면들처럼 기기 날짜 기준으로 해도 됨, 보고에 적기)
  - 시각만 있고 시간대가 null(교외)이거나 날짜만이면 날짜로만: 마감일 다음 날 0시에 지남
- 문구

| 경우 | 문구 |
|---|---|
| 시각·시간대 있음, 2일 이상 | 'D-3 · 12월 1일 10:00 마감' |
| 시각·시간대 있음, 내일·12:00 전 마감 | '내일 10:00 마감' |
| 시각·시간대 있음, 오늘·시각 전 | '오늘 10:00 마감' |
| 시각 있음·시간대 null | 'D-3 · 11월 30일 18:00 마감' / 당일 '오늘 18:00 마감'(지남 판정은 날짜로) |
| 날짜만 | 'D-3 · 11월 30일 마감' / 당일 '오늘 마감 · 시각 미상' |
| 지남 | '마감 지남' |
| 마감 없음(상태 미확인 포함) | '마감일 미상' |
| closed / removed | '모집 끝남' / '학교 공지에서 삭제됨' |

- 'D-N'의 N은 날짜끼리의 차(지금 `daysLeft`와 같음). 내일이면 'D-1'이 아니라 위 '내일' 규칙(12:00 전 마감)만 따로, 그 밖의 내일은 'D-1 · …'

**테스트**: 위 표의 모든 행을 가짜 시계로. 특히 10:00 마감 당일 09:59 '오늘 10:00 마감' → 10:01 '마감 지남'. 날짜만 마감은 당일 23:59까지 '오늘 마감 · 시각 미상', 다음 날 0시 '마감 지남'. 신청 시작 전·후, 순서 3·5(saved와 preparing의 조건 확인 위치)

## 4. 단계 3: 공고 리포트 '내 지원' 카드, 상세 분석 머리 한 줄

- 리포트: 저장한 공고에만, 상태 칩 아래에 카드 하나
  - 위: 상태 칩(`stateLabel`) + 남은 날(`remaining`)
  - 가운데: 다음 할 일 한 줄(`next.text`). 그 아래 `items` 나머지를 작은 글자로(최대 3줄)
  - 버튼(상태별)
    - saved: '준비 시작'(주) · '이번엔 안 함'
    - preparing: 다음 할 일에 url이 있으면 그 이름('신청 사이트 열기'·'원문 열기')(주) · '신청함' · '이번엔 안 함'
    - applied·skipped: '되돌리기'
    - missed·closed·removed: 버튼 없음
    - preparing인데 열 링크가 없으면(원문 없는 알림톡) '신청함'이 주 버튼(팀장 승인 2026-11-24)
    - '신청함'·'이번엔 안 함'을 누르면 짧은 알림에 '되돌리기'(팀장 승인 2026-11-24)
  - '신청함'·'이번엔 안 함'은 짧은 알림(스낵바 등, 지금 저장 알림과 같은 모양)에 '되돌리기'
  - 마감 변경: 카드를 그리면 `seenDeadline`을 지금 마감으로 기록(다음부터 저장함·홈 변경 표시가 사라짐). 리포트 맨 위 마감 변경 배너는 지금 그대로 두되, 이미 본 변경이면 그리지 않음
  - 아래 고정 버튼(학교 공지에서 보기 / 신청 사이트 열기)은 그대로
- 상세 분석 화면: 분석 카드들 위에 한 줄 '내 지원 · {stateLabel} · {next.text} · {remaining}'. 저장 안 한 공고면 없음. 누르면 아무것도 안 함(리포트로 돌아가면 카드가 있음)
- 문구는 ui-style §2(명사형·합쇼체). 색·글자 크기는 ui-style 토큰만(새 토큰 금지)

**테스트**: 상태별 버튼, 전이 뒤 카드 문구, 되돌리기, 저장 안 한 공고엔 카드 없음, 상세 분석 머리 줄이 카드와 같은 문자열

## 5. 단계 4: 저장함

- 줄마다: 상태 칩 + 다음 할 일(없으면 생략) + 남은 날. 지금 메타 줄의 남은 날·'모집 마감'·'공고에 마감일 없음'·'마감일 지남'·'모집 상태 미확인'은 `remaining`으로 바꿈
- 마감 설명 원문(선착순 등)은 저장함 줄에서 뺀다. 리포트 일정에서만 보임(팀장 승인 2026-11-24)
- 지원 건 줄은 메타 줄 아래에 상태 칩 + 다음 할 일. 오른쪽 북마크(저장 취소) 버튼은 그대로 둠(팀장 승인 2026-11-24). 북마크를 칩으로 바꾸는 것은 달력만
- 묶음: 지금 묶음(이번 주 마감 / 다음 주 마감 / 그 이후 / 마감일 없음)에 진행 중 지원 건(saved·preparing)만. 끝난 지원 건(applied·skipped·missed·closed·removed)은 맨 아래 '끝난 지원' 묶음(지금의 '지난 공고' 자리)
- removed 줄의 '학교 공지에서 삭제됨' + '목록에서 지우기'는 지금 그대로
- 마감 변경 말풍선·'마감일 바뀜' 칩: `seenDeadline`과 지금 마감이 다를 때만(리포트를 열면 사라짐). 지금처럼 모집 중(open)일 때만

**테스트**: 상태별 묶음, 끝난 지원 묶음, 변경 표시가 리포트를 연 뒤 사라짐

## 6. 단계 5: 달력

- 강조: 진행 중 지원 건(saved·preparing)의 마감일은 지금 저장 점(채운 점) 그대로 + 그날 목록 맨 위
- 신청 시작 줄: 진행 중 지원 건의 `applicationStart` 날짜에 그날 목록 '신청 시작' 줄(점은 더하지 않음). **일정이 밀리면 이 줄을 두 번째로 뺌**(§8)
- 흐리게: applied(칩 '신청함', 글자 `muted`). 신청함 줄은 채운 점을 그리지 않음(팀장 승인 2026-11-24)
- 지원 건 줄은 북마크 아이콘 대신 상태 칩
- 뺌: skipped·missed·closed·removed
- 저장 안 한 맞춤 공고(테두리 점)는 그대로
- 행의 남은 날: 지원 건이면 `remaining`(지금은 모집 중이 아니면 모두 '마감')

**테스트**: 상태별 표시·빠짐, 신청 시작 줄, 맞춤 공고는 그대로

## 7. 단계 6: 홈·브리핑 (마지막)

- `home_sections.dart`
  - '이번 주 마감' 후보에서 끝난 지원 건을 뺌(추천 목록에 같은 공고가 있어도 뺌)
  - `HomeRow`에 지원 건이면 `CaseView`를 붙이고, 줄의 제목 위 '저장한 공고' 표시 대신 상태 칩, 메타 마지막 칸은 추천 이유 대신 `next.text`, 맨 앞 남은 날은 `remaining`
  - `HomeNudge`에 `startToday` 추가: 지원 건 중 saved·preparing이고 `applicationStart` 날짜가 오늘인 것 수(저장한 공고만, 팀장 결정 2). `dueToday`에서 끝난 지원 건을 뺌
  - 말풍선 순서: 오늘 마감 → 신청 시작 → 마감 변경 → 새 공고. 예 '오늘 마감 1건 · 신청 시작 2건'. 공고 제목은 넣지 않음(D-050 그대로)
  - 말풍선이 보이면 브리핑이 비어 있지 않아야 한다는 기존 조건을 지킴(브리핑에 신청 시작 소식이 들어가야 함)
- 브리핑(`briefing_data.dart`·`briefing_screen.dart`): '저장 곧 마감'에서 끝난 지원 건을 빼고 날짜 문구를 `remaining`으로. 신청 시작 소식(지원 건만) 추가. 지원 건 카드는 하루 최대 3개(마감 가까운 순). **일정이 밀리면 브리핑 변경을 먼저 뺌**(§8). 그때도 말풍선 '신청 시작' 건수와 브리핑이 비어 있지 않아야 한다는 조건이 어긋나지 않게, 브리핑을 빼면 말풍선의 신청 시작 건수도 빼고 보고
- 강조 하루 1번: 말풍선 건수·브리핑 카드에 들어간 지원 건은 그날 `emphasizedOn`을 기록하고, 같은 날 다시 세지 않음(목록 줄 표시는 상한 없음). 하루 첫 화면 기준
- 리마인드 시점(앱 안만): 신청 시작일 당일, 마감 2일 전~당일(지금 브리핑 '저장 곧 마감'의 2일 기준 그대로)

**테스트**: 끝난 지원 건이 이번 주 마감·말풍선·브리핑에 없음, 신청 시작 건수, 하루 1번 강조, 브리핑 3개 상한

## 8. 병렬·일정이 밀릴 때

- 병렬: 1·2는 홈 병합과 상관없이 바로. 2 뒤 3·4·5는 파일이 달라 동시에 가능. 6은 2 뒤(홈 한 목록이 이미 기준 브랜치에 있어야 함). 7의 화면 간 비교 테스트는 3~6 뒤
- 일정이 밀리면 자를 순서(팀장 결정): ① 브리핑 변경 → ② 달력 신청 시작 줄. 홈은 자르지 않음

## 9. 검증과 보고

## 10. 알려진 한계

- 공고 문서가 서버에서 사라지면 저장 목록 응답에서 빠져, 다른 기기에서 저장을 취소한 것과 구분할 수 없다. 그래서 그 지원 건 기록은 지운다(신청함 기록도 함께 사라짐). 게시된 채 삭제된 공고(lifecycle removed)는 '학교 공지에서 삭제됨'으로 남는다
- 신청 시작·신청 사이트는 상세를 받기 전(저장 직후 받기 실패 등)에는 화면에 나오지 않는다

- 판정은 추천 목록(최대 50건)에 들어온 공고만 받는다. 추천 목록에 한 번도 없었던 공고(관련 없는 저장 공고, 학교를 바꾼 뒤의 다른 학교 공지 등)는 계속 null이라 '지원 조건 직접 확인' 항목이 나오지 않는다. 판정을 서버에서 따로 받으려면 저장 목록 응답에 판정을 붙이는 계약 변경이 필요(12/8 이후 검토)
- 마지막으로 받은 뒤 공고 조건이 바뀌었어도 그 공고가 추천 목록에 다시 나오기 전까지는 예전 판정이 남는다(받은 시각은 함께 기록)
