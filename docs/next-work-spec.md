## 1. 목표와 범위

M1에서 실제 공고가 Android 목록·상세·원문까지 연결되도록 출처, 개발환경, 계약, 역할 경계를 먼저 합의합니다. 다음 작업은 아래 작업 단위로 따로 요청하고 검토합니다.

이 문서 작성으로 특정 출처·버전·인증 수단·서버·라이브러리가 승인되지는 않습니다. 공통 계약은 이유·생산자와 소비자 영향·호환성을 PR 또는 이슈에 먼저 적고 팀장 승인 후 작성합니다. SPEC에 없는 세부사항은 아래 결정 질문에 답을 남긴 뒤 반영합니다.

앱·서버 구현, 실제 수집 실행, Firebase 리소스 생성·배포, CI 추가는 이번 문서 작성 범위 밖입니다. 다중 출처 확대, 임베딩·학습 추천, 푸시, 캘린더, iOS 등 SPEC §2의 제외 항목도 추가하지 않습니다.

## 2. 현재 출발점

- 비공개 GitHub 저장소와 초기 7개 파일, PR 템플릿이 준비되어 있습니다.
- `docs/handoff.md`의 GitHub 설정 결과는 이전 인수인계 브랜치의 기록입니다. 병합 여부는 작업 착수 시 확인합니다.
- 앱·백엔드 코드, `contracts/`, `fixtures/`는 아직 없습니다. `docs/decisions.md`는 이 문서 작성 후 T1 합의안(미확정)으로 생성했습니다.
- 출처 이용조건, 실행 버전, 인증 수단, 서버 실행 환경, 공통 코드 사전은 미확정입니다.
- main 보호 설정은 GitHub HTTP 403으로 적용되지 않았습니다. 기능 브랜치와 팀장 PR 검토 규칙을 지킵니다.

## 4. 작업별 명세

### T1. SPEC와 역할 경계 합의

근거: SPEC §3·§8·§12.

- 산출물 제안: `docs/decisions.md`의 개발 범위·담당 합의 항목.
- SPEC v0.1의 채택 여부와 보류 쟁점을 기록합니다. 문서 작성 사실을 팀 합의로 간주하지 않습니다.
- 팀장은 분석·검증·추천·Firebase·보안·통합을, 팀원은 어댑터 1개와 Flutter 화면을 맡는 제안을 검토합니다.
- 팀원 부담이 큰 경우 SPEC §8에 따라 팀장이 수집 파이프라인·배포를 맡는 분담을 결정합니다.
- 파일 소유권과 공동 파일 변경 절차를 확인합니다. 계약과 사전은 팀장 주도로 변경합니다.

완료 기준: 합의 날짜·참여자·결정·이유·담당·보류 항목이 기록되고 양측이 확인합니다. SPEC 변경이 필요하면 공통 계약 변경 절차를 별도로 따릅니다.

### T2. 첫 출처 확인·신청

근거: SPEC §2·§6 수집·분석·§12.

- 산출물 제안: `docs/source-review.md`의 첫 출처 검토 기록.
- 명지전문대 공개 게시판 1개를 원래 목표로 두고 정확한 게시판 URL, 제공 주체, 확인 날짜를 기록합니다.
- 자동 접근·수집·저장·앱 재표시·외부 LLM 전달·첨부 처리의 허용 범위를 각각 확인합니다. 미확인은 미확인으로 남깁니다.
- 확인한 이용조건의 원문 링크, 허가 신청 여부·날짜, 답변 여부·근거를 기록합니다. 이 문서만으로 신청을 전송하지 않습니다.
- 허가가 지연되면 공식 API 후보의 이용조건과 접근 절차를 확인해 대체 출처 선정안을 제시합니다. 비용·추가 서비스 승인이 필요하면 결정 전에 명시합니다.
- 출처 시간대의 근거, 수집 빈도·재시도 제한의 출처 측 제약을 조사합니다. 실제 적용 값은 합의 후 설정합니다.

완료 기준: 원래 출처의 승인·대기·불가 상태와 근거가 있고, 허용 범위가 확인된 출처만 활성화하도록 착수 조건이 정리됩니다. 허가 대기 시 검토·신청 작업 완료와 실제 수집 차단 상태를 구분합니다. 대체 출처로 연결한 결과를 교내 연동 완료로 보고하지 않습니다.

### T3. 개발환경·인증·서버 결정

근거: SPEC §4·§10·§12.

- 산출물 제안: `docs/decisions.md`의 기술 결정 항목.
- Flutter·Dart·Python의 정확한 버전, Android 개발·검증 환경, 의존성 고정 방법을 합의합니다. 후보 호환성 확인과 실제 설치·실행 결과를 구분합니다.
- Firebase Authentication에서 사용할 로그인 수단을 결정합니다. 사용자 식별은 인증 정보에서 얻는 원칙을 유지합니다.
- Cloud Run과 Cloud Functions 중 서버 실행 환경 하나를 선정합니다. 이유, 배치와 요청 처리의 경계, 인증 검증·개발환경 분리를 기록합니다.
- 로컬 LLM 후보의 실행 방식·라이선스·평가 방법을 정리합니다. 최종 품질 판단은 M1 전 실제 평가 결과로 남깁니다.
- 수집 빈도·재시도 상한·오래된 정보 표시 기준의 결정 담당과 확인 시점을 기록합니다. 확정 목표는 M1 전입니다.
- 라이브러리 추가가 필요하면 용도·대안·라이선스·비용을 제시하고 승인을 받습니다. 유료 API를 기본 의존성으로 정하지 않습니다.

완료 기준: 확정값과 미정값이 분리되고, 결정마다 날짜·결정자·이유·영향·확인 근거가 기록됩니다. `.env.example`은 실제 확정된 변수의 이름·설명만 후속 작업에서 갱신합니다. 기술 선정이 클라우드 생성·배포 승인을 대신하지 않습니다.

### T4. 공통 계약과 사전 코드 합의

근거: SPEC §5~§7·§12, AGENTS §3.

- 산출물 제안: `docs/decisions.md`의 계약 합의 항목과 이를 검토하는 PR 또는 이슈.
- RawNotice, Notice, EligibilityCondition, UserProfile, RecommendationItem, SavedNotice별 필드 의미를 SPEC에서 추적합니다.
- 학교·학과·관심사·직무·카테고리 코드의 초기 범위, 관리 위치, 변경 담당을 합의합니다. 실제 코드값과 사용자 정보를 추정하지 않습니다.
- 스키마 표현 방식, 필수·선택·nullable 필드, 버전·식별자·검증 정책을 합의합니다.
- 논리 Repository 인터페이스를 기준으로 샘플과 실제 구현의 교체 경계를 확인합니다. 실제 HTTP 경로·Firestore 접근 방식은 서버 결정 후 계약과 함께 확정합니다.
- PR 또는 이슈에 수집기 → 분석·검증 → 추천 → 앱의 생산자·소비자 영향과 초기 도입의 호환성 영향을 적습니다.

완료 기준: 아래 미정 사항의 결정 또는 보류 범위가 명확하고, T5에서 구현할 계약 범위를 팀장이 승인합니다. 결정되지 않은 규칙은 스키마나 샘플에 임의로 넣지 않습니다.

### T5. JSON Schema·샘플·검증 연결

근거: SPEC §5·§6·§7·§11, AGENTS §3.

- 산출물: 팀장이 승인한 초기 계약 묶음. `contracts/`, `fixtures/`, 관련 SPEC 문서·검증 코드의 정확한 파일 목록은 T4에서 정합니다.
- 최초 스키마 버전은 SPEC의 초기 `1.0` 기준을 따릅니다. 버전 변경이 필요하면 변경 절차로 합의합니다.
- 승인된 스키마와 공통 사전으로 유효 샘플·오류 샘플을 작성합니다. 합성 자료임을 명시하고 실제 사용자 개인정보를 넣지 않습니다.
- 스키마 검증과 의미 검증을 구분합니다. 스키마 통과를 날짜 해석·원문 근거·지원 조건의 정확성으로 간주하지 않습니다.
- 같은 PR에서 필요한 SPEC 문서·스키마·샘플·소비 코드를 맞춥니다. 승인된 런타임·검증 도구로 실행한 명령, 통과·실패 건수, 예상 오류를 기록합니다.
- 실제 수집기·추천기·앱 소비자가 아직 없으면 부재를 명시합니다. 샘플 검증 결과와 실제 소비자 통합 검증 결과를 구분하고 후자는 M1 작업표에 남깁니다.

계약·후속 소비자 검증에 포함할 사례:

| 사례 | 기대 규칙 | 확인할 경계 |
|---|---|---|
| 날짜만 있음·시간대 미상 | time/timezone 미상 보존, 임의 23:59·Asia/Seoul 부여 금지 | 분석 → Notice → 앱 |
| 조건 빈 배열·불완전 추출·첨부 미처리 | 자동으로 제한 없음·met으로 취급하지 않음 | 분석 → 조건 비교 |
| 명시적 제한 없음 | 조건 미발견과 구분하고 원문 근거 보존 | 분석 → 조건 비교 |
| 검증된 필수 조건 불충족과 미확인 조건 공존 | 확실한 불충족이 있으면 not_met | 조건 비교 → 추천 |
| 불충족 없이 미입력·미해석 존재 | needs_check | 조건 비교 → 앱 |
| 전체 필수 조건 해석·충족 확인 | met | 조건 비교 → 앱 |
| 공고 재수집·내용 변경 | 동일 내용은 중복 없음, 변경본은 버전 구분 | 수집 → 파이프라인 |
| 분석 실패·단일 403 | 예전 분석을 최신처럼 표시하지 않음, 삭제 확정 금지 | 파이프라인 → 앱 |
| review_pending·closed·removed·not_met | 기본 추천에서 제외 | 추천 → 피드 |
| 평가 불가 요소·동점 | 분모 제외, 모두 불가하면 점수 없음, 게시일·ID 정렬 | 추천 → 피드 |
| 저장 후 마감·조건 변경 | 최신 공고 연결, 스냅샷은 변경 안내에 사용 | 저장 → 상세·목록 |

완료 기준: 승인 범위의 정상 샘플은 통과하고 오류 샘플은 의도한 이유로 거부됩니다. 의미 규칙의 구현·검증 여부와 아직 없는 소비자가 명시되어야 합니다. 계약 검증만으로 위 전체 흐름이 구현됐다고 보고하지 않습니다.
