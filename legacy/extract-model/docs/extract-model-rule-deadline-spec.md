## 3. 코드 수정 범위

1. `backend/analysis/extract_model.py`
   - `analyze`에서 `_deadline` 호출을 없애고, `_deadline` 메서드와 마감 관련 import도 지움
   - `decides_deadline = True` 속성을 지움
   - 모듈 설명의 합치는 방식에서 "신청 마감: 모델만" 문단을 "신청 마감: 모델이 정하지 않음(규칙·Gemma, D-055)"으로 바꿈
2. `backend/analysis/kakao.py`
   - `fill_dates`의 마감 보충을 `cf77439`처럼 늘 켬
   - `_decides_deadline`과 `deadline` 인자는 쓰는 곳이 없어지면 지움
3. `backend/analysis/llm.py`
   - 자체 모델과 함께 쓸 때(`extract=False`)도 **마감 보충은 지금 운영처럼 함**
   - 꺼지는 것은 조건·직접 확인 조건 보충만
   - 행정 공지는 지금처럼 요약만
   - 분기를 "요약 / 마감 보충 / 조건 보충"으로 나눠 읽기 쉽게 정리하되, 마감 보충 코드 자체(근거 확인, `is_activity_line`, 규칙 파서)는 바꾸지 않음
   - 버전 꼬리 `-summary`는 실제 동작과 맞게 이름을 바꿈(예: `-nocond`)
4. 분석 버전
   - 11/25 되돌린 버전 문자열(`rule-0.11+extract-v1+ollama:…-summary`)과 반드시 달라야 함
   - 규칙은 바꾸지 않으므로 `ANALYSIS_VERSION`은 `rule-0.11` 그대로
   - 3의 꼬리 변경으로 구분되는지 확인하고 PR에 적음
5. 수집기 `__main__`·`run_batch.ps1`·`pyproject.toml`·`uv.lock`은 바꾸지 않음(분석기 조립은 #104 그대로)

## 5. 검증 (PR에 숫자로 적음)

1. **pytest**
   - `uv run --group extract pytest backend`와 torch 없이 `uv run --isolated pytest backend` 모두 통과(건수)
   - `--basetemp`는 `data/local/` 아래 임시 폴더(샌드박스 제약)
2. **`tools/validate_contracts.py`** 통과
3. **사라진 59건 재확인**
   - `data/local/extract_apply_1125/diag/lost59.json`의 59건을 새 코드로 다시 분석. 원문은 `data/local/backup_extract_20261125/pipeline/records.json`
   - Gemma는 끄고 규칙 + 자체 모델만으로 돌림
   - 합격: 59건 모두 마감 날짜가 같은 조건의 `rule-0.10` 규칙 결과와 같음
4. **복사본 건조 실행 1회**(이전 명세 §6과 같은 방식)
   - 대상: 메인 `data/local`을 새로 복사한 폴더, Firestore 없음, Gemma 켬
   - 순서: `run_batch.ps1` 순서대로 명지 게시판 → 숭의 → 교외 → 알림톡
   - 백업 `notices.json`과 공고별로 비교해 아래를 셈
     - 마감이 사라진 공고 수
     - 마감 날짜가 바뀐 공고 수
     - 마감이 새로 생긴 공고 수
   - 합격: **사라짐 0건**
   - 마감이 바뀌었거나 새로 생긴 공고는 한 건씩 원문과 대조함
     - 원문의 신청 마감과 날짜·시각이 맞는지 봄
     - 행사일·활동 기간·근로 기간 등 신청 마감이 아닌 날짜를 잡았는지 봄
     - 공고 ID, 전 값, 후 값, 근거 문구, 판정(맞음/새 오탐/판정 불가)을 표로 적음. Gemma 보충 결과가 달라진 경우면 그렇다고 적음
     - **새 오탐(틀린 날짜·시각, 신청 마감이 아닌 날짜)이 1건이라도 있으면 반영을 멈추고 보고**. 판정 불가는 사례로만 적음
   - 직접 확인 조건 변화는 출처별 건수를 적음
   - **알림톡 조건 표본 검토**(사람 정답 20건이 게시판뿐이라 보충함)
     - 백업 대비 자격 조건이나 직접 확인 조건이 바뀐 알림톡 공고를 모두 모음. 20건이 넘으면 공고 ID 순으로 정렬해 고정 시드(42)로 20건만 뽑음
     - 각 공고에서 **추가된** 구조 조건(재학 상태·학년·학교)과 **사라진** 조건(구조 조건·직접 확인 조건 모두)을 원문과 대조해, 원문에 근거가 있는지 봄
     - 공고 ID, 추가·사라진 조건, 근거 줄, 판정(맞음/틀림/판정 불가)을 표로 적음
     - 합격: 원문에 없는 제한이 추가된 경우 0건, 원문에 맞는 조건이 사라진 경우 0건. 1건이라도 있으면 멈추고 보고
5. **시험 94건**(`data/local/extract_distill/compare.py`)
   - 이번 동작에 맞는 채점이 필요하면 `compare.py`에 새 하위 명령을 더함. 기존 명령·결과 파일은 덮어쓰지 않음
   - 기준: 마감은 저장된 규칙+Gemma 결과(`compare_out/gemma`, 맞음 77 / 놓침 2 / 틀림 3 / 만듦 12)와 같음
   - 기타 조건: 재현 80% 이상, **정밀도는 지금 운영(규칙+Gemma, 11/24 재측정 62%, 73/118) 이상**. 둘 다 같은 94건·같은 `compare.py` 채점으로 잼
   - 참고: #104 분석기는 11/24에 정밀도 60%(87/145)였음. 이번 동작에서도 62% 아래면 기준 미달로 멈추고 보고(문턱을 고쳐 맞추지 않음)
6. **공통 평가셋 명지 사람 정답 20건**
   - 마감 정밀도·재현율은 규칙과 같음
   - 구조 조건 정밀도는 규칙 이상(10/13 이상)
7. **되돌리기 리허설은 하지 않음.** 절차가 이전 명세 §7-6과 같고 11/24에 이미 확인함

못 넘기는 항목이 있으면 사례를 적고 멈춤(문턱·규칙을 더 고쳐 맞추지 않음).
